# check-docs

設計書（`design/v0/docs/`）の機械検査。番号・リンク・文字のような、機械で拾える食い違いを見つける。**読むだけで、ファイルは書き換えない。**

2026-10-25 の整合性の調査（`design/v0/think/audit-2026-10-25.md`）で見つかった食い違い52件の多くが、機械で拾える型だったため、2026-10-26 に作った（設計スレッドの提案、利用者の承認）。

## 使い方

リポジトリのどこからでも実行できる。Python 3.8 以降、標準ライブラリだけで動く。ネットワークは使わない。

```
python tools/check-docs/check_docs.py              # 検査する（design/v0/ で実行するときのパス）
python tools/check-docs/check_docs.py --next       # 判断ポイントの次の番号を表示して終わる
python tools/check-docs/test_check_docs.py         # 負例テスト（一時フォルダで行う。リポジトリの文書は変えない）
```

- 終了コード: 0 = エラーなし（警告・注はあってよい）、1 = エラーあり、2 = 許可リストの誤り（理由のない項目など）
- `--root DIR`: リポジトリのルートの代わりに DIR を見る（テスト用）。`--allowlist FILE`: 許可リストの代わりに FILE を使う
- 判断ポイントを追記する前に `--next` で次の番号を確かめる（教訓4-51）。次の番号は、文書に書かない

## 検査の内容

| 検査 | 内容 | 結果の種類 |
|---|---|---|
| A1 | 判断ポイントの表（5系統。`docs/implementation-guide.md` §8）の、番号の重複・欠番・並び順の乱れ。依頼文の補完・仮定（`request-text.md` §6）も同じに見る | エラー |
| A2 | `specifications/song-file.md` §10 の番号が、`decisions/ui-and-nonfunctional.md` §7 に実在するか | エラー |
| A3 | 相対リンク切れ。Markdown のリンクと、バッククォートの中の `./`・`../` で始まるパス | エラー |
| A4 | 文字の破損: U+FFFD（置換文字）、`\uXXXX` のまま残った日本語（かな・漢字・全角の範囲）、全角数字、CR | エラー |
| A5 | 「次の番号」の記載。実際の次の番号と違えば警告、合っていても注（値は文書に書かない約束のため） | 警告・注 |

### 判断ポイントの表の読み方（A1・A2・`--next`）

- 系統と節は `check_docs.py` の `SYSTEMS` にある。節は、見出し（例: `## 7. 判断ポイント`）から次の `## ` の見出しまで
- 行は、表の1つ目のセルが番号のもの（取り消し線 `~~15~~` や太字も数える）。「17・18」「23〜55」のような範囲のセルは、番号の行として数えない（範囲を指す参照の行のため）
- **語彙の系統**は、`decisions/presets.md` §6 と `decisions/vocabulary/README.md` §5 の通し番号（§8 の定義）。2つのファイルの行を合わせて、1から最大まで欠番がないこと、本体の行が1つだけであることを見る。並び順はファイルごとに見る
  - 一方のファイルに置いた**参照の行**（2つ目のセルが「（…）」で、3つ目のセルが「→」で始まる行。例: `| 59 | （分類の見出し名の扱い） | → vocabulary/README.md |`）は、本体の行として数えない。参照の行の番号には、もう一方のファイルに本体の行が要る
- 次の番号は、本体の行の最大に1を足したもの
- `song-file.md` §10 は、保存に関わる番号だけを載せた要約の表で、欠番は見ない（A2 は実在だけを見る）

### 対象のファイル（A3〜A5）

- Markdown: `design/v0/docs/` 配下のすべての `.md`、リポジトリ直下の `CLAUDE.md`、`design/v0/tools/*/README.md`
- JSON（A4 だけ）: `design/v0/docs/specifications/` 配下のすべての `.json`（`presets/` を含む）
- A3 は、コードブロック（3連のバッククォートで囲んだ部分）の中と、`*`・`{}`・`<>`・`…` を含むパス（雛形の書き方）を見ない
- A4 の CR は、作業ツリーのファイルを見る（Git の中身ではない）
- A5 は、次を数えない: `docs/discussions/`・`docs/examples/`（時系列の記録）、引き継ぎ書の追記の行（`- 2026-10-25 追記36…` のように始まる行）と §8（前回までの引き継ぎ）以降
- A5 の系統は、記載の直前にある語（ファイル名や「補完・仮定」など。`SYSTEM_KEYWORDS`）で決める。決められないときは警告

## 許可リスト（`allowlist.json`）

意図した例や、過去からある欠番などは、許可リストに**理由つき**で入れる。理由（`reason`）のない項目は、設定の誤り（終了コード2）になる。どの検出にも当たらなくなった項目は「使われていない許可」として警告する（消し忘れを防ぐ）。

| キー | 項目の形 | 照合のしかた |
|---|---|---|
| `a1` | `{"system": "ui", "kind": "missing", "number": 12, "reason": "…"}` | 系統の id・種類・番号 |
| `a2` | `{"file": "…", "contains": "…", "reason": "…"}` | ファイルと、行に含まれる文字列 |
| `a3` | `{"file": "design/v0/docs/…", "path": "./assets/…", "reason": "…"}` | ファイルと、パスそのもの |
| `a4` | `{"file": "…", "kind": "fwdigit", "contains": "…", "reason": "…"}` | ファイル・種類（`fffd`・`uesc`・`fwdigit`・`cr`）・行に含まれる文字列。`cr` はファイル単位で `contains` を書かない |
| `a5` | `{"file": "…", "contains": "…", "reason": "…"}` | ファイルと、行に含まれる文字列 |

- 系統の id: `vocab`・`input`・`ui`・`tool`・`text`・`text-aux`。A1 の種類: `missing`・`duplicate`・`order`・`dangling-pointer`
- 行番号ではなく、行の内容で特定する（文書の編集で行がずれても外れない）
- 新しく見つかった食い違いのうち、すぐには直さないもの（設計スレッドの判断待ち）は、理由を「保留（日付。判断待ち）…」として入れ、報告する

## 定期の整合性の調査

この検査で拾えない食い違い（同じ事実の写しの古さ、片側だけで決めた設計など）は、節目ごとの整合性の調査で見る。依頼文の雛形は `audit-request.md`、節目は `design/v0/docs/implementation-guide.md` §7。

## 足すとき・変えるとき

- 判断ポイントの系統や節の見出しを変えたら、`SYSTEMS` を直す
- 検査を足したら、`test_check_docs.py` に負例を足し、検査を壊して検出できることを確かめる（教訓4-13・4-17）
- 2026-10-26 の作成時は、テスト31件、変異24種をすべて検出した
