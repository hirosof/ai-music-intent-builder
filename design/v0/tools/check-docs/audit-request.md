# 整合性の調査の依頼文（雛形）

定期の整合性の調査で、Claude Code に渡す依頼文の雛形。2026-10-25 の調査（`design/v0/think/audit-2026-10-25.md`）の依頼文を一般化した（2026-10-26。設計スレッドの提案、利用者の承認）。

- 実施する節目: 実装の単位の完了時、設計スレッドを移すとき、利用者が求めたとき（`design/v0/docs/implementation-guide.md` §7）
- 使い方: 下のコードブロックを貼る。`YYYY-MM-DD` を実施日に、「前回の報告ファイル」を直近の `design/v0/think/audit-*.md` に置き換える。重点を足すときは「今回の重点」に書く

```
設計書（design/v0/docs/）とリポジトリ全体の整合性を調査してください。今回は調査だけです。報告のファイル以外は、書き換え・コミットをしないでください。

## 背景
設計スレッド（claude.ai。リポジトリのファイルを直接編集する）と Claude Code の両方が、同じ文書を書き換えています。文書間・文書と実装の間に食い違いが出ていないかを、定期に確かめます。
- 範囲: 前回の調査（前回の報告ファイル: design/v0/think/audit-YYYY-MM-DD.md）以降の変更を重点的に見る。前回の報告で「保留」「直していない」とした項目が、今どうなっているかも見る
- 今回の重点: （あれば書く）

## 調べること
A. 判断ポイントの表（5系統。implementation-guide.md §8）
  - 番号の重複・欠番・並び順の乱れは check_docs.py（A1・A2）が見る。その結果に加えて、check_docs.py が見ないもの（表の列の数と見出しの不一致、取り消し線・矢印の付け忘れ、同じ番号の行どうしの中身の食い違い〔song-file.md §10 と ui-and-nonfunctional.md §7 など〕）を見る
  - 次の番号は check_docs.py --next で確かめる。文書に「次の番号」の値が書かれていないか（A5。追記〔履歴〕の中は除く）
B. 判断ポイントの反映先
  - 前回以降に足した判断ポイントの内容が、決定（decisions/）と仕様（specifications/）の両方に反映されているか、内容が食い違っていないか
C. 状態の記述
  - 「未着手」「未検証」「未確認」「未実装」「判断待ち」などの記述のうち、実際には済んでいるもの、またはその逆。git log と突き合わせる
D. 仕様と実装の食い違い
  - 前回以降に足した判断ポイントの分について、実装が仕様どおりか
E. 文書の登録とリンク
  - docs/README.md・decisions/README.md への登録漏れ。相対リンク切れは check_docs.py（A3）の結果を使う
F. 機械検査（結果の件数を報告）
  - git status（未コミットの変更があるか。設計スレッドの書き込みは未コミットのことがある）
  - check_fields.py（--song song.example.json も）、test_check_fields.py（jsonschema あり）、build_presets.py --check、export_parity_cases.py --check
  - check_docs.py（検査ごとの件数と、許可リストで除いた件数。使われていない許可）、test_check_docs.py
  - アプリのテスト・型検査・lint・整形・ビルド
G. 文字の破損
  - check_docs.py（A4）の結果に加えて、機械で判定できないもの（意図しない「かな」の混入など）を、前回以降に変わった箇所で見る（教訓4-22・4-27・4-48）
H. 片側だけが書き換える文書による乖離
  設計スレッドは handoff-next-thread.md を、Claude Code は CLAUDE.md・implementation-guide.md を主に読みます。
  H1. 片側だけが読む文書の情報の遅れ
    - 同じ事実の置き場所の規則（implementation-guide.md §7 の6）に照らして、置き場所でない文書に、事実の写し（実装の完了・テストの件数・宿題の状態・判断ポイントの中身など）が増えていないか。写しがあれば、正の文書と一致しているか
  H2. 片側だけで決めた設計
    - Claude Code が記録した判断ポイント、または実装中に決めた細部で、設計スレッドの記録（handoff の宿題一覧・追記、decisions/README.md）に載っていないもの。承認の経緯（誰が・いつ）が書かれているか
    - 設計スレッドが決めた内容で、implementation-guide.md（§6 の受け入れ基準、§7 の往復の手順、§10 の教訓）に反映されていないもの
  H3. 判断ポイントを経ないデータの変更
    - 前回以降に変わった仕様データ（specifications/ 配下の JSON。presets/ は build_presets.py --check で確認済みなら除く）について、変更ごとに対応する判断ポイントまたは記録があるか
  - どちらが書いたかは git の作者では区別できない。コミットメッセージ（「設計:」で始まるものは設計スレッドの変更）、記録の書きぶり、日付から推定し、推定であることと根拠を添える。判定できないものは「不明」とする

## 報告の形
- 報告は design/v0/think/audit-YYYY-MM-DD.md に書く（このファイルだけは新規作成してよい）
- 食い違いは1件ずつ、次の形で書く: 番号／場所（ファイルと節）／内容／どちらが正と見られるか／根拠（コミット、記録の日付など）／修正案
- 食い違いは次の3つに分ける。H の結果も、A〜G とは別の節に、同じ3分類で書く
  1. 機械的に直せるもの
  2. どちらが正か記録から決まるもの
  3. 判断が要るもの
- 確かめた結果、食い違いがなかったものは、件数に含めず別の節に書く
- 調べなかった範囲、時間の都合で浅くしか見ていない範囲は、その旨を明記する（教訓4-40）
- 補完・仮定一覧と暗黙の前提を付ける
- 最後に、チャットにも要約（件数と、判断が要るものの一覧）を出す
```

## 2026-10-25 の依頼文との違い

- 範囲を「2026-10-18（リポジトリへの移動）以降」から「前回の調査以降」にした
- 機械で拾える検査（番号・リンク・文字・次の番号の記載）は `check_docs.py` に任せ、人が見るのはその外側にした
- H1 を、同じ事実の置き場所の規則（`implementation-guide.md` §7 の6。2026-10-26）に照らして見る形にした
- 「確かめた結果、食い違いがなかったもの」を別の節に書くことを足した（2026-10-25 の報告で、件数の数え方をそろえるために行った形）
