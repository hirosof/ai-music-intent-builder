## 1. 用語と、4種類の保存

| 用語 | 意味 |
|---|---|
| 楽曲データ | 1曲分の入力内容。`{ schemaVersion, requests[] }`。**すべての保存の中身は、この形を1つだけ定義する** |
| 依頼（request） | 楽曲データの要素。1つの依頼文に対応する（新規生成または派生生成。DP-05） |
| ユーザープロファイル | 利用者が名前を付けて保存した楽曲データ（`{ name, updatedAt, data }`）。旧称「設定プロファイル」。プロジェクトファイルに近い。ツールプロファイル（R-10）とは別物（判断ポイント18） |
| ファクトリープロファイル | アプリに同梱する楽曲データ（同じ `{ name, updatedAt, data }`）。入力の見本・起点で、書き換えられない（§4-4。判断ポイント19） |
| エクスポートファイル | 書き出すファイル。**常に**プロファイルの配列を持つ形（単一は要素1、一括は N。判断ポイント11） |
| 楽曲ファイル | プロファイルを1件だけ含むエクスポートファイルの通称 |

| 種類 | 保存先 | 中身 | 個数 |
|---|---|---|---|
| 自動保存 | localStorage | 楽曲データ | 1 |
| ユーザープロファイル | localStorage | プロファイルのストア（§4） | 複数（1つのキーに配列で持つ） |
| ファイル入出力 | ダウンロード／読み込み | エクスポートファイル（§4） | 任意 |
| UI 設定 | localStorage（別のキー） | UI 設定（§5） | 1 |

素の楽曲データがファイルとして現れることはない。現れるのは、自動保存と、プロファイルの `data` の中だけ。ファクトリープロファイルは利用者の保存ではなく同梱データなので、保存の種類には数えない（§4-4）。

## 2. 楽曲データ

```json
{
  "schemaVersion": 1,
  "requests": [
    {
      "id": "r1",
      "toolId": "suno",
      "toolVersion": "v6",
      "generationType": "new",
      "vocalMode": "instrumental",
      "lyricsAuthor": null,
      "derivedFrom": null,
      "axes": { "...": "input-items.md §5" },
      "output": { "...": "input-items.md §3・§5" }
    }
  ]
}
```

### 2-1. 最上位

| キー | 必須 | 内容 |
|---|---|---|
| `schemaVersion` | ○ | 整数（初版は 1）。楽曲データの形の版（§6） |
| `requests` | ○ | 依頼の配列。**1件以上**。順序に意味はない（依頼どうしの関係は `derivedFrom` が表す） |

楽曲データは名前を持たない（名前はプロファイルの側。判断ポイント15）。

### 2-2. 依頼（request）

要素側に置くのは、段階（新規／派生）ごとに変わりうるため（DP-05）。

| キー | 必須 | 型・取れる値 | 内容 |
|---|---|---|---|
| `id` | ○ | 文字列。`^[a-z0-9-]{1,32}$` | 楽曲データ内で一意。`derivedFrom` から参照される。**生成方法は実装に任せる**（`crypto.randomUUID` は HTTPS かローカルホスト以外では使えず、LAN 名の http で配信するローカル IIS で失敗しうるため、依存しない） |
| `toolId` | ○ | 文字列 | 対象ツール。初版は `suno` のみ |
| `toolVersion` | ○ | 文字列 | 依頼を作ったときの、対象ツールの版（例: `v6`）。§7 |
| `generationType` | ○ | `new` ／ `derived` | 新規生成／派生生成 |
| `vocalMode` | ○ | `instrumental` ／ `vocal` | ボーカル区分（R-02） |
| `lyricsAuthor` | ○ | `chat-ai`／`chat-ai-instruction`／`null` | 作詞の主体（L-01a。2026-09-28 決定済み。`input-items.md` 判断ポイント20）。`vocalMode = vocal` のとき①指定必須（②お任せを持たない）。`vocalMode = instrumental` のときは `null`。`vocalMode` との整合はチェッカーが検証する（宿題38） |
| `derivedFrom` | ○ | `null` ／ オブジェクト（§3） | 派生元 |
| `axes` | ○ | オブジェクト | 楽曲の入力項目。形は `input-items.md` §5 |
| `output` | ○ | オブジェクト | 出力の制御。形は `input-items.md` §5。依頼文の範囲 `requestScope`（`combined`／`style`／`lyrics`）もここに置く（§2-3） |

### 2-3. 初版の制約（形式と、初版が扱える範囲を分ける）

スキーマは、将来の値も含めた**形式**を表す（`requests` は1件以上、`generationType` は `new`／`derived`、`vocalMode` は `instrumental`／`vocal`）。初版が扱えるのは次の範囲で、**チェッカー（§9）が縛る**。派生生成のときに、スキーマではなくチェッカーを緩める。

- `requests` はちょうど1件
- `generationType` は `new`、`derivedFrom` は `null`（派生生成は初版の対象外。F6）。**2026-10-18、初版は新規生成のみと確定**（`../decisions/scope.md` L-01b。派生生成は第2段階。`../handoff-next-thread.md` 宿題48）
- `vocalMode`・`lyricsAuthor` は、歌あり対応（L-01。宿題38）で初版の対象になった。`vocalMode = vocal` のとき `lyricsAuthor` は `chat-ai`／`chat-ai-instruction` のいずれかが必須、`instrumental` のときは `null`（F12）。歌あり専用・インスト専用の `axes` 項目（`lyricsTheme`・`lyricsLanguage`・`lyricsStructure`・`structure`）に、無効な方の①指定があるのもエラー（S6）
- **2026-10-16 実装**: 上の `vocalMode`・`lyricsAuthor` の整合は `check_fields.py` の F12・S6 が検証する（宿題38。F6 からは外した）
- **2026-10-18 追加（候補7。`input-items.md`〈decisions〉判断ポイント28）**: `output.requestScope`（`combined`／`style`／`lyrics`。省略は `combined`）。`style`・`lyrics` は `vocalMode = vocal` のときだけ取れる（インストは `combined` のみ。F13）。1つの楽曲データが2つの依頼文（スタイル用・歌詞用）を表せる。`requests[]` は複製しない（派生関係のための配列。DP-05）。`lyricsAuthor` は `lyrics` でも使い、`style` では使わない（値は保持してよい）。スキーマは `output` を自由なオブジェクトのままとし、取れる値はチェッカー（O2）が見るため、**`song.schema.json` は変更しない**

## 3. 派生元（`derivedFrom`。判断ポイント12・23〜27）

`derivedFrom` は `null`、または次のオブジェクト（2026-09-23、判断ポイント23〜27で改訂。`discussions/2026-09/16_derived-generation-data-model.md`）。

```json
"derivedFrom": {
  "source": "internal",
  "requestId": "r1",
  "operation": "edit-vocals",
  "sourceStyleText": null,
  "sourceStyleEditMethod": { "state": "delegated" },
  "sourceStyleCloseness": { "state": "delegated" },
  "originalLength": null
}
```

| キー | 必須 | 内容 |
|---|---|---|
| `source` | ○ | `internal`（同じ楽曲データ内の別の依頼が元曲）／`external`（このツールの外で作った曲が元曲）。判断ポイント23（A1） |
| `requestId` | `source = internal` のとき○、`external` のとき持たない | 同じ楽曲データ内の、別の依頼の `id`。自分自身を指さない。循環しない |
| `externalSourceLabel` | `source = external` のとき任意 | 元曲を識別するための自由記述（名前・メモ）。項目名・文字数上限は未定（判断ポイント23。§3-2 参照） |
| `operation` | ○ | 派生生成の操作種別（R-02）。文字列の id、または `null` |
| `sourceStyleText` | 任意 | 元曲の実際のスタイルテキスト（自由記述）。`source` の値に関わらず使える。判断ポイント24（B1） |
| `sourceStyleEditMethod` | 任意。`input-items.md` §1 と同じ状態モデル（①指定／②お任せ） | 元のスタイルの編集方法。値は `keep`（完全保持し要素の追加のみ）／`change`（変更する）。`sourceStyleText` が空なら項目ごと無効（依頼文には出さない）。判断ポイント26（H） |
| `sourceStyleCloseness` | 任意。同上の状態モデル | 元のスタイルとの近さ。値は `near`／`far`。`sourceStyleEditMethod` が `change` のときのみ有効。`sourceStyleText` が空なら項目ごと無効。判断ポイント26（H） |
| `originalLength` | 任意 | 元曲の長さの実値（秒の正の整数）、または `null`（持たない）。`source: internal` のときは参照先 `request` の `axes.length` を入力時の初期値の候補として提示してよいが、自動流用はしない（利用者が確認・修正する）。判断ポイント27（G1） |

- `operation` の値は、`null`、または、ツールプロファイル（`tool-profile.md` §4-3）の `derived` モードの操作のうち `scope` が `candidate`／`first` のものの id。F9 が検証する。例の `edit-vocals` は、Suno の「ボーカルを編集」（暫定値だった `add-vocal` から変えた）
- **整合規則**: `generationType` が `new` ⇔ `derivedFrom` が `null`。`derived` ⇔ オブジェクト
- **整合規則（2026-09-23 追加）**: `source = internal` ⇔ `requestId` を持つ・`externalSourceLabel` を持たない。`source = external` ⇔ `requestId` を持たない
- **整合規則（2026-09-23 追加）**: `sourceStyleCloseness` が①指定のとき、`sourceStyleEditMethod` は `change`（①指定または②お任せの導出結果が `change`）でなければならない。チェッカー（F11）が矛盾（エラー）とするのは、`sourceStyleEditMethod` が①指定の `keep` の場合だけ。②お任せ・省略は矛盾としない（省略時の初期状態が未確定のため。§3-2）
- 初版では常に `null`。型（文字列からオブジェクトへ）を後から変えると移行が要るため、いま形を決めた

### 3-2. 未確定のまま残す点（2026-09-23）

- `externalSourceLabel` の項目名・文字数上限
- `sourceStyleEditMethod`・`sourceStyleCloseness` の初期状態（①②のどちらを既定にするか）
- `extend` 操作での `length` パラメータの意味（延長後の合計か、追加する秒数か）。`tool-profile.md` §13 の未整理事項のまま

詳細な経緯は `discussions/2026-09/16_derived-generation-data-model.md` を参照。

## 4. プロファイル・ストア・エクスポートファイル

### 4-1. プロファイルの形（ユーザー・ファクトリー共通）

```json
{ "name": "和風戦闘BGM", "updatedAt": "2026-09-21T10:00:00+09:00", "data": { "...": "楽曲データ（§2）" } }
```

| キー | 必須 | 内容 |
|---|---|---|
| `id` | ○（ユーザー。版2から） | 文字列。空でない。ストア内・ファイル内で一意。作るときは UUID（`crypto.randomUUID()`）。**検査は形式を縛らない**（2026-10-31。判断ポイント68）。取り込むときは常に新しい id を振る |
| `folderId` | ○（ユーザー。版2から） | 所属するフォルダの `id`、または `null`（ルート）（§4-6。判断ポイント68） |
| `name` | ○ | 文字列。空でない。**同じフォルダの中で一意**（2026-10-31 に「ストア内・ファイル内で一意」から緩めた。判断ポイント68。元は判断ポイント15） |
| `updatedAt` | ○ | ISO 8601 の日時（タイムゾーン付き） |
| `data` | ○ | 楽曲データそのもの（判断ポイント10）。`data` 自身が `schemaVersion` を持つ |

ファクトリープロファイル（§4-4）は、`id`・`folderId` を持たない（読み取り専用で、組み込みの名前で特定できるため）。

### 4-2. ストアとエクスポートファイル

ストア（localStorage のプロファイル一覧）とファイルは、ほぼ同じ形（判断ポイント11）。書き出しに変換は要らない。

```json
{ "schemaVersion": 2, "folders": [ ... ], "profiles": [ ... ] }
```

```json
{ "schemaVersion": 2, "exportType": "profiles", "exportedAt": "2026-09-21T10:00:00+09:00", "folders": [ ... ], "profiles": [ ... ] }
```

**版2（2026-10-31。判断ポイント68）**: `folders` とプロファイルの `id`・`folderId` を足した。版1 は `folders` を持たず、プロファイルは `id`・`folderId` を持たない。版1 → 版2 の移行は、各プロファイルに新しい id を振り、`folderId` を `null` にし、`folders` を空にする（§6）。これが最初の版上げで、移行の仕組みはこのときに作る（§6-4）。

| キー | ストア | ファイル | 内容 |
|---|---|---|---|
| `schemaVersion` | ○ | ○ | 整数。**この外側の形**（ストア／ファイル）の版。`data` の版とは別（§6） |
| `exportType` | — | ○ | ファイルの内容の種類。**`profiles` のみ**。単一・一括の区別ではない（単一は `profiles` が1要素）。UI 設定などを書き出す必要が出たら、値を足す |
| `exportedAt` | — | ○ | 書き出した日時（ISO 8601） |
| `folders` | ○（版2。0件以上） | ○（版2。0件以上） | フォルダの配列（§4-6）。ファイルには、入れたプロファイルが属するフォルダ（祖先を含む）だけを入れる。ただし、フォルダを選んで書き出すときは、選んだフォルダとその配下のすべてのフォルダ（空のサブフォルダを含む）も入れる（2026-11-01。Claude Code の持ち帰り〔段階3 `ebe19b7`〕、利用者の判断・承認）。ファイルにはプロファイルが1件以上要る |
| `profiles` | ○（0件以上） | ○（1件以上） | プロファイルの配列 |

### 4-3. 取り込みの操作（`ui-and-nonfunctional.md` §4-3）

- **追加**: ファイルのプロファイルを、ストアに加える。名前が衝突したときの操作（上書き、別名、取り込まない）は UI 仕様で決める。データ上の規定は「名前は一意」だけ
- **置換**: ストアの内容を、ファイルの内容で入れ替える。自動保存には触れない
- **取り込み先とフォルダ構成**（2026-10-31。`ui-and-nonfunctional.md` 判断ポイント69）: 取り込み先のフォルダを選ぶ（管理画面から開いたときは今見ているフォルダ、ヘッダーから開いたときはルートが初期値）。版1 のファイルは、全件が取り込み先に入る。版2 のファイルは、チェック「フォルダ構成を保つ」（初期値オン）がオンなら、ファイルのフォルダ構成を取り込み先の下に再現する（同じ名前のフォルダが既にあれば、そこに合流する）。オフなら、全件を取り込み先に入れる。名前の衝突は、入る先のフォルダの中で判定する。取り込んだプロファイルとフォルダには、常に新しい id を振る。**ただし、衝突で「上書き」を選んだときは、ストアにあったプロファイルの `id` と位置を保ち、中身だけを入れ替える**（新しい id を振るのは、新しく加わるもの〔追加・別名〕。判断ポイント69 の細部 (b)（2026-10-31。Claude Code の持ち帰り〔段階1 `458d696`〕、利用者の承認））。**置換との関係**（2026-11-01。Claude Code の持ち帰り〔段階2 `8ff30dc`〕、利用者の承認）: (e) 「フォルダ構成を保つ」は置換にも当てる（オフなら全件をルートに入れる。そのとき名前が重なれば、書き込む前の検査〔F5〕で止まり、理由を出して何も書き込まない）。(f) 取り込み先のフォルダは、追加（と追加して開く）にだけ効く。置換はストア全体をファイルの内容で入れ替えるので使わない（欄の見出しは「取り込み先のフォルダ（追加するとき）」）。(g) 「フォルダ構成を保つ」は、版2 のファイルなら常に出す（選んだプロファイルがすべてルートにあっても出す。版1 のファイルでは出さない）
- **選択と直接開く**（2026-10-30。`ui-and-nonfunctional.md` 判断ポイント65）: 「追加」「置換」は、ファイルの中から選んだプロファイルだけを対象にする。1件だけ選んだときは、編集中の内容（自動保存）として開ける（「開く〔保存しない〕」はストアに入れない。「追加して開く」は追加のあとに開く）。どちらもデータの形は変えない
- **読み込みで受け付ける形**（2026-10-19。判断ポイント46）: エクスポートファイル（`exportType: "profiles"`）だけ。素の楽曲データ・ストアの形は、理由つきで拒否する。`check_fields.py` の形の自動判別（§9-2）は、検証ツールとして残す

### 4-4. ファクトリープロファイル（判断ポイント19）

アプリに同梱する、入力の見本・起点（利用者の保存ではない）。**形と規則は判断ポイント19で、中身（6件）は判断ポイント39〜40で決めた。**

- 形は、同梱のエクスポートファイル（`exportType: "profiles"`）と同じ。読み込みの処理・スキーマ・チェッカーをそのまま使う。アプリと一緒に配備されるため、常に現在の版で、移行は要らない（**2026-10-31 に改めた**: 保存データの版2 の導入後も、同梱ファイルは版1 の形のまま置き、読むときに移行する。版2 のプロファイルは `id`・`folderId` が必須だが、ファクトリーはこれを持たないため。判断ポイント68 の細部 (a)）
- 読み込みは、**編集中の内容（自動保存）への読み込みだけ**。ファクトリー自体は書き換えない。編集したければ、ユーザープロファイルとして保存する
- エクスポートと「置換」の対象外（同梱物のため）
- 名前の一意性は、ファクトリーとユーザーで別々に持つ。一覧も別に表示する
- 複製した後は独立し、複製元は記録しない
- `toolVersion` は、同梱時の対象ツールの版（初版は `v6`）
- 「入力例」であり、Suno での実測に基づく推奨（DP-06）とは別物として扱う
- 中身は `factory-profiles.json`（判断ポイント39〜40）: 6件（ボス戦BGM（和風オーケストラ）／作業用BGM（ローファイ）／村のテーマ（フォーク調）／Vlog・日常動画BGM（明るいアコースティック）／瞑想用BGM（アンビエント）／技術解説動画BGM（テクノ））。全件 Suno v6・新規生成・インスト・依頼1件。1件目は `song.example.json` の `data` と同じ。26項目のすべてを、少なくとも1件が①指定で使う

### 4-5. 将来の追加候補（初版にはない。判断ポイント20〜22）

**階層（フォルダ）は、2026-10-31 に F2（パス文字列）ではなく、id と親の参照の形で導入した（§4-6。`ui-and-nonfunctional.md` 判断ポイント68）。** 下の表の階層の行は、検討時の記録として残す。ラベルは未導入（宿題56）。

初版は、階層・ラベル・プロジェクトのいずれも持たない。どれも加法的に足せる（プロファイルのラッパーやストアへの任意キー、`exportType` の値。形を変えるときは §6 の規則で版を上げる）。三者は**別々の軸**で、階層・ラベル・プロジェクトを互いの代わりにしない。

| 軸 | 初版 | 将来の候補 | 備考 |
|---|---|---|---|
| 階層（フォルダ） | なし（名前の検索と並び替えのみ） | プロファイルのラッパーに `folder`（パス文字列。例 `ゲーム/ボス戦`）を持つ（F2） | `name` とは別のキー。`/` を禁止する必要があるのは、階層側の名前だけ |
| ラベル | なし | 複数付けられる単純なラベル | 階層とは別物 |
| プロジェクト | なし | まず P1'（属性なし。`projects[]` と、プロファイルの `projectId`）。必要なら P2-a（共通設定を、曲の新規作成時に複製する）。P2-b（継承）は最後の手段 | 下記 |

`name` の文字は、今は制限しない（フォルダの導入後も同じ。フォルダは id で参照するので、`name` に `/` を含めてよい）。禁止文字を後から足すのは、既存のファイルの `name` を無効にする「締める変更」になるため。パス形式（`name` に階層を含める形）に決めた場合は、その時点で制限を決め直す。

プロジェクトについて（判断ポイント22）:

- 階層とは別の概念（作業の範囲）。独立した一覧（`projects[]`）を id で参照する。フォルダ（F2）は、プロジェクト内の整理として併存できる
- **既定では、他のプロジェクトのプロファイルを隠す**（切り替えで全表示にできる。語彙の表示切り替え R-19 と同じ流儀）。隠すのは表示の絞り込みで、データの境界ではない。エクスポートと「置換」の範囲は別に決める（既定は全体。隠したまま書き出すと、バックアップが不完全になるため）
- 現在のプロジェクトは、UI 設定に持たせる案が自然（不明な id は無視する規則が既にある。§5）
- 名前の一意性は、ストア全体からプロジェクト内へ緩められる（緩める変更なので、既存のファイルは有効なまま）
- プロジェクトに属さないプロファイル（初版の全件、ファクトリー）の扱い（「未分類」を常に見せるなど）は、導入時に決める
- P2-b（継承）は、「省略なら初期状態」の規則（`input-items.md` §5）や、再現性（曲のファイルだけで依頼文を再現できること）と衝突する。RP-02 の状態区分の見直しが要るため、必要になってから決める
- **所属の情報（フォルダ、ラベル、プロジェクト）は、楽曲データ（`data`）の外**（プロファイルのラッパーやストア）に置く。楽曲データは、自動保存やファクトリープロファイルの中でも使われ、それらは所属を持たないため

### 4-6. フォルダ（2026-10-31。`ui-and-nonfunctional.md` 判断ポイント68）

```json
{ "id": "…", "parentId": null, "name": "ゲーム" }
```

| キー | 必須 | 内容 |
|---|---|---|
| `id` | ○ | 文字列。空でない。ストア内・ファイル内で一意（フォルダの id どうし）。作るときは UUID。検査は形式を縛らない |
| `parentId` | ○ | 親のフォルダの `id`、または `null`（ルート直下） |
| `name` | ○ | 文字列。前後の空白を除いて空でない。**同じ親の中で一意**（兄弟のフォルダどうし） |

- ユーザープロファイルだけがフォルダに属する。フォルダは、空でも残せる
- 親は実在するフォルダ。循環してはならない（自分自身・自分の配下を親にできない）
- 深さの上限は設けない
- 所属の情報は楽曲データ（`data`）の外に置く（§4-5 の方針のまま）

## 5. UI 設定（判断ポイント16）

```json
{ "schemaVersion": 1, "termVisibility": { "genre": { "trip-hop": true, "edm": false }, "instrument": { "helicon": true } } }
```

| キー | 必須 | 内容 |
|---|---|---|
| `schemaVersion` | ○ | 整数 |
| `termVisibility` | ○ | 語ごとの表示の有無。`{ 語彙 id: { 語 id: true｜false } }`。語彙の既定値から**変えたものだけ**を持つ（`presets.md` §6-2、`decisions/presets.md` §11-3） |

- **不明な語彙 id・語 id は、エラーにせず無視する**。語彙は楽曲データと別に更新され、UI 設定は表示のためだけで、失っても楽曲の内容が変わらないため（楽曲データでは、不明な id は拒否する。§6）

- 楽曲データ・プロファイル・エクスポートファイルには含めない。初版はファイル入出力の対象外

## 6. schemaVersion と読み込みの規則（判断ポイント13）

`schemaVersion` は、次の3つの対象が**それぞれ独立に**持つ。

| 対象 | 版が表すもの |
|---|---|
| 楽曲データ（自動保存の値、プロファイルの `data`） | 楽曲データの形 |
| ストア／エクスポートファイル | 外側の形（`profiles` の配列、プロファイルの形） |
| UI 設定 | UI 設定の形 |

### 6-1. 版を上げるとき

- **保存データの形（キー、型、取れる値）を変えるたびに上げる。** 古い読み手が、読めないものを読めると誤認しないため
- **語彙や項目定義への追加（新しい語 id・項目 id）では上げない。** 保存データの形は変わらない。古い読み手は、6-2 の 4 で拒否する
- 語 id・項目 id の改名・削除は、移行の対象（語 id は再利用しない。V-08）

### 6-2. 読み込み（ファイル入力・ストア・自動保存）

1. **新しい版**（アプリが知る版より大きい）→ **拒否**する。部分的に読まない
2. **古い版** → 楽曲データの版とストア／ファイルの版を別々に、`n→n+1` を1段ずつ移行する。移行が未定義の段があれば拒否する
3. **版がない、または整数でない** → 拒否する
4. **楽曲データの中の項目 id・語 id が不明** → 拒否し、不明な id を列挙する。**理由**: `exclude` の語を黙って落とすと、除外したはずの要素が依頼文に入る
5. ファイルのうち1つでも拒否になったら、ファイル全体を拒否する（一部のプロファイルだけを取り込まない）
6. **ストアを拒否したときは、そのストアに書き込まない**（2026-10-19。判断ポイント44）。プロファイルの保存・削除・取り込みを止め、拒否の理由を示す。空として扱って保存すると、既存のプロファイルを上書きして消すため。ファイルへの「書き出す」は、名前を付けてファイルにだけ行う（`../decisions/ui-and-nonfunctional.md` §4-7）
7. **古い版のストアを移行して読んだときは、新しい版で書き戻す。書き戻しに失敗しても（容量超過など）、読み込みは止めず、通知も出さない。** 次に保存などで書き込むときに新しい版で書く。書き戻せない間は、読むたびに移行し直す（版1 → 2 では id も読むたびに振り直される。編集中の内容との対応は画面の中だけで覚え、保存しないので実害はない。判断ポイント68 の細部 (d)（2026-10-31。Claude Code の持ち帰り〔段階1 `458d696`〕、利用者の承認））

### 6-3. 自動保存（`ui-and-nonfunctional.md` §4-1 の精密化）

**移行できれば移行し、できなければ破棄する。** §4-1 の「不一致なら破棄」を「移行不能なら破棄」に精密化したもの。初版は移行が存在しないため、動作は同じ。理由: 自動保存の目的は作業の保全であり、GitHub Pages への配備で、利用者の操作なしに版が上がりうるため。

**自動保存の読み込みだけ、「未完成」を許す（2026-10-19。判断ポイント43）**: 編集途中に自然に起こる状態を失わないよう、自動保存の読み込みでは、次の2つを拒否の理由にしない（未完成として読み込み、画面で示し、依頼文は生成しない）: **S5**（①指定なのに値が空）、**F12**（`vocalMode = vocal` で `lyricsAuthor` が `null`）。他のエラーは拒否・破棄のまま。**保存側は厳格**: ユーザープロファイルへの保存とファイルへの書き出しは、エラー0件のときだけ許す（警告は許す）。プロファイル・ファイルの読み込みは、従来どおり S5・F12 も拒否する。`check_fields.py` は厳格のままで、この緩和はアプリの自動保存読み込みだけにある。

**保存時の正規化（2026-10-19。判断ポイント45）**: 保存する楽曲データ（自動保存・プロファイル・書き出し）は、(1) ①指定以外の項目は値を持たない、(2) 今の `vocalMode` で無効な項目（S6）は、状態に関わらず省略する（判断ポイント61）、(3) インストのとき `requestScope` は `combined`、`lyricsAuthor` は `null`、という形に正規化してから保存する。`output` のその他の値は触らない（`../decisions/ui-and-nonfunctional.md` §4-7）。

### 6-4. 初版の実装範囲

**規則だけを今決め、移行の実装は、最初の版上げのときに行う。** 初版は版 1 のみで、移行する対象がない。画像版 Phase 5 の教訓（保存の枠を後回しにして、必要になってから作った）に対しては、規則の記録と、「版を上げるときは、移行を追加するか、未対応と明記する」という運用で応える。

## 7. ツールと版の比較（判断ポイント14）

| 対象 | 規則 |
|---|---|

## 8. localStorage のキー

localStorage は**オリジン単位**（パスは含まない）。GitHub Pages で他のツール（画像版など）と同じ `github.io` を共有している場合、キーが衝突しうる。

- キーには**接頭辞を付ける**。実際の文字列は実装で決める（本書は「付ける」ことだけを定める）
- キーは3つ: 自動保存、プロファイルのストア、UI 設定（種類ごとに別のキー）。このほかに、VueUse が管理するカラーモードのキーが1つある（UI 設定には含めない。接頭辞を付ける。付けられないとわかったときは既定キーのままを例外として記録。`../decisions/ui-and-nonfunctional.md` §4-7、判断ポイント47）。**2026-10-19（U4e）: Nuxt UI の `ColorModeSelect` に保存キーを渡せないため、既定キー `vueuse-color-scheme` のまま（例外）**
- 各キーの値は JSON（UTF-8。DP-07）で、それぞれ、楽曲データ、ストア、UI 設定の形

GitHub Pages 版とローカル版は、オリジンが違うため共有されない（`ui-and-nonfunctional.md` §6）。2つの配備の版が違うことがありうるため、ファイル入出力（§6 の読み込みの規則）が両者の橋渡しになる。

## 12. 暗黙の前提と残る論点

- **未保存の編集内容をそのままファイルに書き出す操作**は、UI 仕様で扱う（プロファイルとして保存させる、名前を入力させる、など）。素の楽曲データをファイルにしない（A1）ことの帰結
- **2026-10-16 訂正**: ~~`vocalMode` と `axes.voiceTreatment` の整合規則は、歌あり対応（L-01）で扱う。初版は `instrumental` のみで、声の扱いは歌詞のない形に限る（`input-items.md` 判断ポイント9）~~ → L-01 が決着し、`voiceTreatment` は歌あり（`vocalMode = vocal`）でも有効（判断ポイント27）、`structure` は歌ありで無効（`lyricsStructure` を使う）、`lyricsTheme`・`lyricsLanguage`・`lyricsStructure` は歌ありのときのみ有効（`fields.json` 側の `note` に記述済み）。これらの `vocalMode`×`axes` の整合は、静的スキーマでは表せないため `check_fields.py` が検証する（宿題38。実装済み（2026-10-16）。F12・S6）
