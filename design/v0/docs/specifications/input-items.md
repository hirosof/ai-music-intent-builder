## 0. 位置づけとファイル構成

`decisions/input-items.md` で決めた項目を、実装が読める形に定義する。含まないもの: 楽曲データの外側の形（`requests[]`、`toolId`、`generationType`、プロファイル、ファイルなど。`song-file.md`）、ツールプロファイル（`tool-profile.md`）、依頼文の生成。

| パス | 内容 | 編集 |
|---|---|---|
| `docs/decisions/input-items.md` | 項目の決定と理由。**正** | 項目の変更はここで決める |
| `docs/specifications/input-items.md` | 本書 | 手書き |
| `docs/specifications/fields.json` | 項目の定義（機械可読） | 手書き。`decisions/input-items.md` と食い違ったら、こちらを直す |
| `docs/specifications/fields.schema.json` | `fields.json` の JSON Schema（draft 2020-12） | 手書き |
| `docs/specifications/song.example.json` | 楽曲データの例（形は `song-file.md`。`axes`・`output` は依頼の要素） | 手書き。検証スクリプトで確認済み |
| `tools/check-fields/check_fields.py` | 項目定義と語彙の整合、楽曲データの検証、項目一覧の表の生成 | 手書き |

```
python tools/check-fields/check_fields.py                       # 項目定義を検証する
python tools/check-fields/check_fields.py --song FILE.json      # 加えて、保存データ（楽曲データ／エクスポートファイル／ストア。形は自動判別。`song-file.md` §9）を検証する

```

`fields.json` は、語彙（`docs/specifications/presets/`）を参照する。語彙を変えたら、このスクリプトも再実行する。

## 1. 値の状態（RP-02）

すべての項目は、次の4状態のいずれかを持つ（判断ポイント12）。

| `state` | 表示名 | 意味 | データに持つ値 |
|---|---|---|---|
| `specified` | 指定 | 利用者が値を決めた | 種類ごとの値（§5） |
| `delegated` | お任せ | チャットAI に決めさせる（または足させない。§2-3） | なし |
| `defaulted` | 既定値 | 既定値をそのまま使う | なし（既定値は項目の定義が持つ） |
| `toolManaged` | ツール任せ | 生成時にツールが決める | なし |

名前を `default`・`tool` にしなかったのは、`default` が JavaScript / TypeScript の予約語だからである。文字列の値やオブジェクトのキーとしては使えるが、変数名や分割代入（`const { default } = ...`）に使うと構文エラーになる。`tool` は保存データの `toolId` と紛らわしい。過去分詞にそろえた（判断ポイント12）。

- 表示名（指定／お任せ／既定値／ツール任せ）は `principles.md` RP-02 のまま。UI では「指定なし」を使わない
- 項目ごとに取れる状態は決まっている（§3 の「状態」列）。取れない状態は不正
- 「使用しない」は状態ではなく、3値の選択肢の値である（`exclude`）

## 2. 項目の定義（`fields.json`）

### 2-1. 項目のキー

| キー | 必須 | 内容 |
|---|---|---|
| `id` | ○ | 項目 id（camelCase）。保存データの `axes` のキー |
| `label` | ○ | 表示名 |
| `group` | ○ | グループ id。グループの `axis` は、語彙の `axis` と一致する |
| `kind` | ○ | §2-2 |
| `vocabulary` | 種類による | 語彙 id（`presets/`）。`select`・`triSelect`・`sectionList` で必須、それ以外は持てない |
| `leaveValues` | — | 「足させない」値の語彙 id の配列。単一選択の項目だけが持つ。この値を依頼文の「値」列に出すときは、末尾に「（足さない。触れないまま残す）」を付ける（`request-blocks.md` §5）。対象は、声の扱い（`no-voice`）、年代・時代感（`no-era`）、想定する聴取環境（`no-playback`）。判断ポイント19 |
| `freeText` | ○ | 項目内の自由記述を持つか（判断ポイント15） |
| `specificity` | ○ | ①指定のときの具体化の許容度（`expand` 拡張可／`adapt` 翻案可／`keep` 保持／`uiSetting` UI設定。`decisions/input-items.md` §1-1） |
| `initialState` | ○ | 新しい楽曲での初期状態。取れる状態のいずれか |
| `states` | ○ | 取れる状態と、状態ごとの定義。`specified` は必須（DP-01） |
| `note` | — | 根拠や注意 |

### 2-2. 種類（`kind`）

| 種類 | 内容 | 語彙 |
|---|---|---|
| `select` | 語彙から1つ選ぶ（＋自由記述） | 必須 |
| `triSelect` | 語彙の各語を「使用する／使用しない／未指定」の3値で選ぶ（＋自由記述） | 必須 |
| `text` | 自由記述 | なし |
| `bpm` | 数値、または範囲（min〜max） | なし |
| `length` | 秒数（範囲はツールプロファイルが持つ。Suno は 10〜360） | なし |
| `sectionList` | 語彙（セクション）の並び | 必須 |

### 2-3. ②お任せの扱い（判断ポイント11・17）

`states.delegated` は、次のどちらかを必ず定義する。

| `rule` | 意味 | 追加のキー |
|---|---|---|
| `derive` | 手がかりから導く | `cues`（手がかりの項目 id の並び。`"*"` は他の項目全体）、`fallback` |
| `leave` | 足さない（`principles.md` RP-11）。指定しないまま残す | なし |

`fallback` は、使える手がかりがないときの扱い。

| `type` | 意味 |
|---|---|
| `omit` | 指定しないまま残す |
| `choose` | 必ず何かを決める（例: 主ジャンル） |
| `value` | 語彙の値（`value`）を使う |
| `text` | 文言（`text`）を使う（例: 用途の「特定の用途を想定しない楽曲」） |

**手がかりの使い方（判断ポイント17）**: 手がかりは、**値が決まっている項目（①指定・③既定値）だけ**を使う。②お任せ・④ツール任せの項目は、手がかりにしない。使える手がかりがなければ `fallback` に従う。すべてが②の場合の最終的な拠り所は用途で、用途も②なら「特定の用途を想定しない楽曲」とする（`request-text.md` B-02 の 2-1）。

この規則により、手がかりが相互に参照していても、問題にならない（現状は主ジャンルと基調となる情緒が互いを挙げている。どちらかが指定されていれば、それを使う）。

「②なら『中程度』」のような記述（`decisions/input-items.md`）は、**手がかりのない導出に、フォールバックを付けたもの**として定義した。②と③は、結果が同じでも意味が違う。②はAIが案ごとに変えてよく、③は変えない（RP-12）。

### 2-4. ③既定値（判断ポイント11）

`states.defaulted` は、**既定値を持つ単一選択の項目だけ**が持つ。既定値（`value`）は語彙の id。既定値のない項目（聴取環境、BPM、構成など）は、③を持たない。

初期状態は②。ただし、次の3項目は違う。

| 項目 | 初期状態 | 理由 |
|---|---|---|
| 声の扱い | ③（`no-voice`） | 歌が入るリスクがあるため、保守的に倒す（判断ポイント9） |
| 様式の寄せ方 | ③（`style`） | `decisions/input-items.md` 判断ポイント6 |
| 長さ | ④ | Auto（RP-02 の④の例） |

## 4. 項目をまたぐ規則（`crossFieldRules`。判断ポイント13・17）

| 規則 | 種類 | 内容 | 重大度 |
|---|---|---|---|
| `purposeDetail-follows-purpose` | `follows-delegated` | 用途が②のとき、用途の詳細は①でも②として扱う（実効状態）。指定が無視されるので警告する | 警告 |
| `styleLean-needs-region` | `active-when` | 地域・文化の様式に「使用する」があるときだけ、様式の寄せ方を依頼文に出す | 情報 |
| `instrument-exclusion-linked` | `linked-exclusion` | **楽器の除外は3項目（主旋律・伴奏・リズム）で連動する。** どれかで「使用しない」にすると、3項目すべてで除外になり、「使用する」は外れる | 警告 |
| `mainGenre-not-excluded` | `single-not-excluded` | 主ジャンルに選んだ語を、副ジャンルで「使用しない」にしていると警告する | 警告 |

**楽器の除外を連動させる理由**: Suno の除外欄は役割別に持てず、「主旋律には使わないが伴奏には使う」は表せない。連動させれば、3値の趣旨（矛盾を入力できない構造にする。`decisions/input-items.md` §1-2）を、複数の項目にまたがっても守れる。UI は、同じ語をどの項目で操作しても同じ状態が変わる形にする（`decisions/presets.md` §4-4 と同じ考え方）。保存データに矛盾があった場合は、読み込み時に RP-04 の「除外優先」で解決し、警告する。

**語彙を共有する項目**は、生成時の検査で、矛盾を扱う規則があることを確かめる（`check_fields.py` の D9）。共有の現状は、ジャンル（主・副）と楽器（3項目）。新しい共有が増えたとき、規則の追加を忘れない。

## 5. 保存データ（`axes`）の値の形（判断ポイント16）

依頼（`requests[]` の要素）の `axes` は、項目 id をキーに、次の形を持つ。楽曲データ全体の形は `song-file.md`。例は `song.example.json`。

```json
"axes": {
  "purpose":         { "state": "specified", "value": "boss-battle-theme" },
  "regionStyles":    { "state": "specified", "choices": { "japanese": "use", "celtic": "exclude" } },
  "voiceTreatment":  { "state": "specified", "value": "wordless-choir" },
  "bpm":             { "state": "specified", "value": { "min": 120, "max": 140 } },
  "structure":       { "state": "specified", "value": ["intro", "theme", "climax", "outro"] },
  "brightness":      { "state": "delegated" },
  "intensity":       { "state": "defaulted" },
  "length":          { "state": "toolManaged" }
}
```

| 種類 | ①指定のときのキー | 規則 |
|---|---|---|
| `select` | `value`（語彙の id）、`freeText` | どちらか一方または両方。`freeText` は自由記述を持つ項目だけ。少なくとも一方は空でない |
| `triSelect` | `choices`（`{語彙の id: "use" \| "exclude"}`）、`freeText` | 「未指定」の語はキーを持たない。`choices` か `freeText` の少なくとも一方は空でない |
| `text` | `value`（文字列） | 空でない |
| `bpm` | `value` | 正の数、または `{ "min", "max" }`（min ≤ max） |
| `length` | `value` | ツールプロファイルの範囲内の整数（秒）。Suno は 10〜360 |
| `sectionList` | `value`（語彙の id の配列） | 空でない。順序に意味がある。同じ語が複数回あってもよい |

- ①指定でない状態は、`state` だけを持つ。`value` などが残っていれば、無視して警告する
- `axes` に項目がなければ、初期状態で、値なしとして扱う
- ①指定なのに値が空なのは不正
- `output` は、出力項目 id をキーに値を持つ（`granularity` は配列）。省略した項目は既定値
- `recommendParams` は `{パラメータ id: 真偽}`（例: `{ "weirdness": true }`。省略した項目はオフ）。キーは、その依頼の `toolId` のプロファイルで `requestRole` が `recommend` のパラメータの id。プロファイルにないキーはエラー（O3）、その依頼のモードにないキーは警告（O4。無視される）。判断ポイント18

## 9. 暗黙の前提と残る論点

- **手がかりの相互参照**（主ジャンル ⇄ 基調となる情緒）: 依頼文（`request-text.md` B-02 の 2-1）は「さらにその上位の手がかりをたどる」と書いており、相互参照では「上位」が定義できない。本書の規則（値が決まっている項目だけを手がかりにする）に合わせて、依頼文の文面を調整する余地がある（未反映）
- **副ジャンル・地域・BPM・構成**は、「AIが足してよい」が表せない（判断ポイント14）
- **項目内の自由記述**は、選択のみの11項目にない（判断ポイント15）。声の扱い、年代のように開いた集合になり得る項目は、検証で足りなければ見直す
- 楽曲データ全体の形は `song-file.md`（完了）、ツールプロファイルは `tool-profile.md`（完了）。依頼文のブロックの仕様は、別作業
- **`recommendParams` の保存値の形**は解決した（判断ポイント18。`{パラメータ id: 真偽}`）。項目の一覧を、依頼のモードにあるものに絞ること（`audio-influence` は remix のみ）は、検証（O4）と、依頼文のブロックが行う
- 項目の画面（並び、グルーピングの見せ方、状態と値をどう見せるか）は UI の仕様で決める。状態（お任せ）を選択肢と同じ部品に並べる見せ方は、候補として挙がっている
