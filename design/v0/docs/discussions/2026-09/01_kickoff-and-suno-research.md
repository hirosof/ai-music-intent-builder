## 2. 音楽版固有の論点（初回の整理）

1. 出力が「1本のプロンプト」ではなく複数フィールドの組になる
2. 超過分は警告なしで切り捨てられる（→ のちに「入力欄で止まる」と解釈を修正）
3. 歌詞という第二の創作物がある
4. アーティスト名の扱いが画像版より厳しい
5. 数値指定（BPM）は確定条件になりにくい
6. 否定指定の置き場所がツールによって違う
7. Gemini 向け要件の音楽版が要るかもしれない
8. 対象ツールの状況が流動的（Udio のダウンロード停止、Stable Audio 3 のオープンウェイト公開など）

## 3. スコープ確認（Q&A）

**Q. 主に使う音楽生成AI は？**
A. **Suno**。「将来的に他のサービスやローカルで動作するものを利用する可能性は否定できないが、
ひとまず Suno を主な対象としたい」

**Q. 歌詞の扱いは？**
A. **インスト中心**＋**AI に作詞まで任せたい**。ただし後者は
「どの AI が作詞を行うかとの観点で」別途議論が必要。

→ R-01 確定、R-02 一部確定。将来拡張の可能性を受け、
ツール固有情報のデータ分離を「提案」から**設計要件**に格上げ（R-10）。

→ 初版（MVP）はインストのみとする提案。ただしボーカル区分の軸はデータ構造に確保。

## 4. L-01（作詞）の構造が変わった

hirosof からの補足:

- (a) アドバンスドモードではスタイルと歌詞が別欄。歌詞欄では Suno 側の AI に
  作詞のみを依頼できる → **パターン B2** の発見。
  チャットAI が出すのは歌詞ではなく「Suno 作詞AI への指示文」になり得る
- (b) 先にインストで作成し、**Remix で歌付きバージョンを作る**方法もある

→ L-01 を3軸に分解（L-01a 作詞の主体 / L-01b 生成の手順 / L-01c 発行の単位）。
画像版 P5-01 の教訓（軸の混在）を踏まえた事前分離。

→ 「段階」という概念が必要に。のちに「新規生成 / 派生生成」として一般化。

## 6. 画面調査（スクリーンショット提供）

### 6-1. その他のオプション（通常時）

スタイルを除外 / ボーカル性別 / 長さ / Max モード / 奇抜さ / スタイルの影響 /
バリエーション / パーソナライズ。曲名欄はオプションの下。

初回のスクリーンショットは既定値ではなく（バリエーション = 最大）、
**取り直し**により既定値は「標準」と判明。

→ 前回「既定値が最大だから、チャットAI の精密なスタイルが大きく再解釈される」とした
リスク強調を**修正**。既定が「標準」なので、そこまで強いリスクではない。
ただし公式 FAQ の「完全に制御するならバリエーションを 0」という記述から、
「標準」でもある程度の再解釈は起こり得る点は維持。

副次的な発見: **リセットアイコンで既定値かどうかを判別できる**（H-04）。

### 6-2. その他のオプション（リミックスモード）

**オーディオの影響**（既定 25%）が追加される。他は通常時と同じ。

→ **Suno の設定項目はモードによって増減する**ことが判明。
プロファイルは「どの項目がどのモードで使えるか」をデータとして表現する必要がある。

### 6-3. リミックス作業後のブラウザ全体

実例: インスト（3:00）→ ボーカルを編集 → Add Vocal 版（2:58〜2:59）。
詳細は `research/suno-profile.md` §5-2。

Q&A:
- リミックス時のスタイル欄 → 元曲のスタイルが最初から入る。
  入力済みの状態で移行する場合は「元曲を反映 / 現在の設定を保持」を選べる
- リミックス時の作詞AI → **使える**（B2 と派生生成の組み合わせが可能）
- 導線 → ワークスペースから D&D、「＋オーディオ」から過去曲選択など複数

### 6-4. 「ボーカルを編集」ドロップダウン

REMIX 4種 + 編集 11種 = 15操作。

→ **スコープの原則**「テキスト指示を伴わない操作は対象外」を導入。
→ 「段階」概念を「新規生成 / 派生生成（操作種別 + 派生元情報）」に一般化。
→ プロファイルに「モード ＞ 操作種別」の2階層と「必要プラン」属性を追加。

### 6-5. 作詞家

「Suno の書き方を導く歌詞ペルソナを保存します」「個性を表す歌詞から作詞家を作成」。
未使用。

→ **アカウントに紐づく要素**という分類を新設
（作詞家 / Voice / Custom Model / パーソナライズ）。
中身をチャットAI が知る方法がないため、「使う／使わない」だけを前提として書く方針。

## 7. 数値・仕様の確定

| 項目 | 経緯 |
|---|---|
| 長さ | 当初「5秒単位」と記録 → **誤り**。スライダーの刻みが5秒で、キーボード入力は1秒単位。10〜360秒 |
| 長さの入力形式 | 「180」→「3:00」、「1:41」→「1:41」。秒数と M:SS の両対応、表示は M:SS に正規化 |
| バリエーション | オフ / 標準 / 高 / 超高 / 最大。既定は標準 |
| 文字数上限 | スタイル 1,000 / 歌詞 5,000 / スタイルを除外 1,000 / 曲名 当初「1,000以上」→ のち **80文字** と確定 / 作詞AI 指示 不明 |

### バリエーションの実例（重要）

入力 `和風戦闘BGM , Choir` / バリエーション「標準」で、2テイクのスタイルが大きく異なった。
詳細は `research/suno-profile.md` §5-1。

→ **バリエーションの設定によってチャットAI が書くスタイルの役割が変わる**ことが確定。
R-12 の中核として、「想定するバリエーション」を依頼文の前提に含める方針に。

→ 「指定なし」の任せ先が**3種類**あることが判明
（チャットAI に補完 / ツール既定値に従う / ツールが生成時に決める）。
のちの RP-02 の4状態区分につながる。

### 文字化けの経緯

`sh?taiko` を「Suno 由来の文字化けかもしれない」と推測し、
依頼文で「不自然な文字は文字化けとして解釈する」ルールを提案 → **撤回**。
原因は Unicode 非対応エディタへのコピーで、正しくは `shōtaiko`。

ただし Suno が書き換えたスタイルには `ō` 等の非 ASCII 文字が実際に含まれるため、
**DP-07（UTF-8 のまま保持）は要件として残った**。

## 8. 参考資料（日本語解説記事2本）の評価

hirosof から共有:
- `https://tech-camp.in/ai-navi/suno-ai/`（更新日 2026-09-03）
- `https://shift-ai.co.jp/blog/22691/`（更新日 2026-09-09）

**更新日は新しいが、内容は v4.5〜v5 期**。実画面と食い違う箇所あり（差分表は
`research/suno-profile.md` §1）。

→ **DP-06**（情報の優先順位）を導入。プロファイルには「対象バージョン」も記録する。

取り込んだ情報:
- 日本語歌詞の発音対策（ひらがな化、ローマ字助詞）→ L-01 で使用
- 歌詞の分量の目安が日本語と英語で食い違う → **推奨長は言語ごとに持つ**必要性
- スタイルの書き方（要素順序、ジャンル結合、楽器の役割）→ RP-06 のひな形候補
- 構成タグと日本語呼称の対応 → R-04 の UI 設計（日本語入力 → 英語タグ変換）
- ジャンル・楽器・ムード用語一覧 → プリセットの参考（そのままは使わない）
- 著作権ルールは**倫理だけでなく生成失敗を防ぐ実務要件**でもある → RP-07

また、Suno 側にもスタイル補助機能（魔法の杖アイコン）がある以上、
本ツールの価値は「スタイルの文章を作ること」ではなく
**要件を構造化して判断のぶれなく伝えること**にあると整理。
