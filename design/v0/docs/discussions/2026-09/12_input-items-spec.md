## 2. 読み直して分かったこと

| 点 | 内容 | 対応 |
|---|---|---|
| ②の意味が2種類 | 「手がかりから導く」と「足さない」（RP-11）。「②なら『中程度』」は、手がかりのない導出にフォールバックを付けたものと読める | 判断ポイント11 |
| ③の既定値が未定義 | ①②③と書かれているのに既定値のない項目があった（聴取環境、BPM、構成） | 判断ポイント11（③を外した） |
| 保存データで決まっていたのは一部だけ | 状態名は `specified` のみ、項目 id は `purpose`・`leadInstruments` の2例のみ | 判断ポイント12・16 |
| 語彙を共有する項目の矛盾 | 楽器3項目（同じ楽器を「使用する」と「使用しない」に分けられる）、主／副ジャンル | 判断ポイント13 |
| 手がかりの相互参照 | 主ジャンルと基調となる情緒が、互いを手がかりにしている（検証スクリプトが検出） | 判断ポイント17 |
| 項目数 | 表を数えると楽曲26＋出力9（判断ポイント4は「約29」） | 補完・仮定に記録 |

## 3. 検討した案と採否

| 論点 | 採用 | 検討した代替案 |
|---|---|---|
| 状態名 | `specified`／`delegated`／`defaulted`／`toolManaged` | 当初案の `default`・`tool`。`default` が JavaScript / TypeScript の予約語（変数名・分割代入で構文エラー）、`tool` が `toolId` と紛らわしいため、利用者の指摘で変更した。実際に JS / TS で試して、文字列の値・キー・enum のメンバーでは問題ないことを確かめた |
| 楽器の矛盾 | 除外を3項目で連動 | 警告のみ（矛盾を入力できてしまう）。役割ごとに楽器を1つの一覧にまとめる再構成（UI の変更が大きい） |
| RP-11 の空白 | 現状のまま | A案と同様に、状態や値を足す。副作用が大きい項目で、AIが勝手に足すのを避けるため保守的に倒した |
| 項目内の自由記述 | 現状のまま | 選択のみの11項目に持たせる。あとから足しても作り直しにならないので、検証後に判断する |
