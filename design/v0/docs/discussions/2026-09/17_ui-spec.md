## 2. 承認された判断

`input-items.md` §2-3（状態の定義）と `kind` ごとの種類（§2-2）を踏まえ、要判断A〜Cを提示した。

| 記号 | 論点 | 決定 |
|---|---|---|
| A1 | 状態表現の基本方式 | kind ごとのハイブリッド方式。`select` 種は、状態を選択肢に混ぜ込む（「お任せ」「既定値（○○）」を疑似選択肢として同じ部品内に提示）。`triSelect`・`text`・`bpm`・`sectionList` 種は、項目ヘッダに状態トグル（セグメントコントロール）を置き、値入力欄はその下に配置する。①以外は値入力欄を無効化する |
| B1 | ③既定値・④ツール任せの見せ方 | 既定値を選択肢リスト内でハイライト表示する（クリック不可のグレー状態）。バッジのみに留めない |
| C1 | 状態変更時の値の保持 | UI 上では値を保持し、①に戻すと復元する。保存データ上は `input-items.md` §5 の規則どおり、①指定以外のときは値を持たない（値が残っていれば無視して警告する）。UI内部の一時保持と、保存データの規則は別に実装する |

D（「足させない」ルールの項目の②表示）は、要判断とせず既定案で決着した。`principles.md` RP-02「UIでは『指定なし』を使わない」に既に反するため、状態ラベルは「お任せ」で統一し、`leaveValues` 系の項目には補助テキスト（例:「AIはこの項目に追加しません」）を出し分ける。

## 5. 分類B: 楽器の除外の連動の見せ方（要判断D）

`input-items.md` §4 の `instrument-exclusion-linked` 規則（主旋律・伴奏・リズムの3項目で除外が連動する）を前提に、画面構成の案を検討した。

| 記号 | 内容 |
|---|---|
| D1（採用） | 統合 1 テーブル。楽器の階層テーブルを 1 つだけ用意し、各行（楽器語）に「主旋律で使う」「伴奏で使う」「リズムで使う」の 3 つのチェック（役割ごとの独立オンオフ）、共通の「除外」ボタン 1 つを横に並べる。除外を押すと 3 チェックがまとめて解除・無効化される |
| D2（不採用） | 3 つの独立テーブル。同期の JS 実装が複雑化する |
| D3（不採用） | 除外専用の共通リストを分離。楽器ごとの確認が 2 画面に分かれ、見通しが悪い |

D1 は、データ上は引き続き 3 つの `axes` 項目（各々 `choices`）に分解して保存するが、画面には 1 つのテーブルとしてしか見せない。Visualizer のインライン試作（楽器名：尺八・和太鼓・ギター・シンセパッドの 4 行で、「ギター」を除外に切り替えると主旋律・伴奏のチェックが自動で外れて無効化される動作）を提示し、利用者から承認を得た。

## 5-2. 分類C: 辞典の画面（要判断E・F）

`decisions/presets.md` §11-5（画面、当時未着手）の候補を前提に、入口・表示形式を検討した。`ui-and-nonfunctional.md` 判断ポイント8（モーダルのネスト禁止）との整合が前提となった。

| 記号 | 内容 |
|---|---|
| E1（採用） | 個別項目内蔵型。既存の階層テーブル試作（`tree-select-prototype-v3`）に実装済みの「非表示の語も表示」トグルが、そのまま辞典の主な入口になる。非表示の語は行展開で理由・代替を同一モーダル内に表示し、別モーダルを開かない。加えて、全語彙横断の独立画面「辞典設定」をダッシュボードのサイドメニュー（Nuxt UI のダッシュボードUIコンポーネント）から開く | 
| E2（不採用） | 辞典を独立モーダルのみに一本化 |

利用者からの追加の指摘を受け、次の2点を反映した。

- 辞典設定はジャンルだけでなく、楽器など他の語彙にも辞典がある（判断ポイント167・190・192・194）ため、辞典設定は語彙ごとのサブ項目を持つ
- 別名（F）: 項目内の階層テーブルでは英語表記だけではピンとこない場合があるため、`aliases` をツールチップで表示する。辞典設定画面は語彙を1つずつ表示するため、`aliases` 列を直接追加する

## 5-3. カラーモード切り替え（要判断H）

利用者から、Nuxt UI にはライト・ダークモード切り替え用のコンポーネントが3種類あるとの指摘を受けて検討した。Web検索で仕様を確認した。

| コンポーネント | 形式 | 選べる状態 |
|---|---|---|
| `ColorModeButton` | アイコンボタン（トグル） | ライト／ダークの2択 |
| `ColorModeSwitch` | スイッチ | ライト／ダークの2択 |
| `ColorModeSelect` | セレクト | システム／ライト／ダークの3択 |

| 記号 | 内容 |
|---|---|
| H1（採用） | `ColorModeSelect`。個人利用ツールでも「OSに合わせる」を既定にできるほうが親切で、明示的にライト/ダークに固定したい場合にも対応できる。配置は辞典設定と同じダッシュボードのサイドメニュー |
| H2（不採用） | `ColorModeButton`。ワンクリックの手軽さはあるがシステム追従を持たない |
| H3（不採用） | `ColorModeSwitch`。H2と同性質で部品の形状のみが違う |

保存先についても確認した。利用者が「Nuxt UIは何もしなくてもローカル保存されるのではないか」と指摘し、Web検索で確認した結果、VueUse の `useColorMode`（Nuxt UI の Vue 版カラーモード連携が内部で使う実装）は既定でローカルストレージ（既定キー `vueuse-color-scheme`）に自動永続化することを確認した（指摘は正しかった）。したがって `ui-settings` への保存は行わず、追加実装も不要とした。

## 5-4. 依頼文のクリップボードコピー

利用者が VueUse の `useClipboard` を見つけ、依頼文のコピーに使えそう（自前実装不要）と指摘した。仕様を確認し、採用した。`copy()` で書き込み、`copied`（一定時間後に自動リセット）でボタンのラベル切り替えを実装できる。

利用者から「HTTPの場合はフォールバックが必要だったはず」との指摘を受け、Web検索で確認した。Clipboard API（`navigator.clipboard`）はセキュアコンテキスト（HTTPS、または `localhost`/`127.0.0.1`）でしか使えない。このプロジェクトは `ui-and-nonfunctional.md` §6 で「GitHub Pages + ローカル IIS」を配置先としているが、ローカル IIS はHTTPで運用され、かつホスト名が `localhost` でない場合（LAN上の別名やIPでのアクセスなど）には Clipboard API が使えないため、指摘は正しかった。したがって `legacy: true`（`document.execCommand('copy')` へのフォールバック）を必須で有効化することにした。

## 5-5. ファイル入出力の実装手段

利用者が VueUse の `useFileDialog`と`useFileSystemAccess`を見つけ、使えそうな場所があるかを確認した。仕様を確認した結果、前者は採用、後者は見送りとした。

- `useFileDialog`: 標準の `<input type="file">` の単なるラッパーで、全ブラウザ対応。`ui-and-nonfunctional.md` §4-3の読み込み（インポート）にそのまま使える
- `useFileSystemAccess`: File System Access API（`showOpenFilePicker`/`showSaveFilePicker`）のラッパーで、同一ファイルへの上書き保存が可能。しかしChromium系（Chrome/Edge/Opera）のみ対応で、Firefox・Safariは非対応（Firefoxは非対応方針を明言）。VueUse側も自動フォールバックは持たない（`isSupported` フラグのみ）

不採用の理由はブラウザ対応の制約のみではなく、現行設計（§4-3。書き出しは常にダウンロード、読み込みは選択して読み込む）では「同一ファイルへの上書き保存」を使う場面がそもそもないことも確認した。将来「保存先を覚えて上書き保存したい」という要望が出た際に、Chromium限定機能として再検討する。

## 5-6. 分類D: 保存関連UI（要判断I・J・K）

`song-file.md` §12の「暗黙の前提と残る論点」に挙げられた5点のうち、分岐の大きな3点を検討した（残り2点は既定案：版の警告・拒否の文言は実装時に文面を決めれば足り、自動保存を破棄したときの通知はトースト1つで十分）。

| 記号 | 内容 |
|---|---|
| I1（採用） | 名前の衝突時（インポート「追加」）は、その都度確認ダイアログ（上書き／別名で追加／取り込まない）を出す。「残りすべてに適用」チェックボックスを添え、一括インポート時の連続確認を避ける |
| J1（採用） | 未保存の編集内容を「書き出す」と、対応するプロファイルがなければ名前入力を促し、命名と同時にユーザープロファイルとして保存してからエクスポートする。`song-file.md` §4-2（A1）の「素の楽曲データはファイルにならない」との整合 |
| K1（採用。ユーザーの指摘で修正） | 当初は「同一画面内で見出し区切り」として提示したが、プロファイル選択は「プロファイル」ボタンから開くポップアップ側で行われるため（別のポップアップが開いていない状態）、ポップアップ内でタブ（ユーザー／ファクトリー）を使うことは容認できるとの指摘を受け、K1を「ポップアップ内タブ分け」に修正して採用した。同一ポップアップ内のタブ切り替えであり、新たなモーダルを重ねるわけではないため、判断ポイント8（モーダルのネスト禁止）とは矛盾しない |

## 5-7. 主要ポップアップの実装コンポーネント（要判断L）

利用者から、Nuxt UIには「ポップアップ」と一言で言っても Modal・Drawer・Popover・Slideover の4種類があるとの指摘を受け、仕様を確認した。

| コンポーネント | 性質 |
|---|---|
| `UModal` | 中央固定のダイアログ。既定でモーダル、オーバーレイあり |
| `UDrawer` | 画面端からスライドする、ドラッグで閉じられるシート。「Scale Background」で背景を縮小させる奥行き演出が可能。モバイルのボトムシートに近い |
| `UPopover` | トリガー要素にアンカーして浮く、非モーダルな軽量表示 |
| `USlideover` | 画面端からスライドする固定パネル。ドラッグ操作なし。大きめの常設パネル向き |

Nuxt UI 公式ドキュメントに「デスクトップは Modal、モバイルは Drawer」を `useMediaQuery` で切り替えるサンプルが公式例として載っており、分類Eで未着手のまま残っていた「実ブラウザでの性能・スマホ幅」の論点の一部に答えを出せそうだった。

| 記号 | 内容 |
|---|---|
| L1（採用） | 「一覧＋ポップアップ方式」のポップアップ全般（カード編集、プロファイル管理など）に、Nuxt UI公式のレスポンシブパターン（デスクトップ幅 `UModal`、モバイル幅 `UDrawer`）を採用。Drawerの「Scale Background」はモバイル側でのみ有効化 |
| L2（不採用） | 幅を問わず Modal に統一 |
| L3（不採用） | 幅を問わず Slideover に統一 |

`USlideover`は今回の主要用途では採用しないが、将来の常設大型パネルの候補として記録する。`UPopover`（非モーダル）は、開いている Modal/Drawer の中で使っても判断ポイント8（モーダルのネスト禁止）には抵触しないことを確認済み。具体的な用途は未確定だが、今後の軽い補足表示の手段として記録する。
