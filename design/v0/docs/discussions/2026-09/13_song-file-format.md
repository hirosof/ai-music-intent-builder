## 3. 検討した案と採否

| 論点 | 採用 | 検討した代替案 |
|---|---|---|
| ファイルの形 | A1: 常に `exportType: "profiles"`（単一は要素1） | A2: 単一は素の楽曲データ、一括は `profiles`。形が2通りになり、名前の置き場所（楽曲データに `name` を入れると、プロファイルの `name` と二重）が要る |
| 操作種別の置き場所 | B1: `derivedFrom: null｜{ requestId, operation }` | B2: `derivedFrom` は id 文字列、`operation` は別キー。B3: ツールプロファイル確定後に追加（R-02 の趣旨に反し、型の変更に移行が要る） |
| schemaVersion | C1: 規則を今決め、移行の実装は最初の版上げ時 | C2: 移行を作らず、一律に拒否・破棄。バックアップ用途（§4-3）と衝突する |
| UI 設定の形 | `{ schemaVersion, termVisibility }` | 引き継ぎ案は語彙 id を最上位に置く。`schemaVersion` と語彙 id が同じ階層に並び、UI 設定を後から足すと形が変わるため、1段足した |
| スキーマの数 | 3本（楽曲データ、エクスポートファイル、UI 設定） | 引き継ぎ案は `song.schema.json` のみ。ファイルと UI 設定の形が加わるため |
| 階層 | 初版はなし。将来の候補は F2（`folder` のパス文字列） | F1（ラベルで代用）、F3（入れ子のオブジェクト。後から変えると最も高くつく） |
| ラベル | 階層とは別の軸（利用者の指摘） | 階層の代わりにラベル |
| プロジェクト | 初版はなし。まず P1'、必要なら P2-a | P2-b（継承）は、「省略なら初期状態」の規則と再現性に衝突するため最後の手段。P3（まとめて依頼）はスコープの拡大 |

**利用者の指摘で決まった点**: 「設定プロファイル」を「ユーザープロファイル」に改め、「ファクトリープロファイル」を足した。ラベルと階層は別、階層の将来の候補は F2、プロジェクトは他のプロジェクトのプロファイルを既定で隠す（表示の絞り込みで、データの境界ではない）。
