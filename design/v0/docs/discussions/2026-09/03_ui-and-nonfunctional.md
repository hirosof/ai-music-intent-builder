## 1. UI 構成: タブ案 → 一覧 + ポップアップ方式

### Claude の当初案（7タブ）

軸ごとに 基本 / 表現 / 音の構成 / 構造 / 除外・補足 / 出力設定 / プレビュー のタブ構成を提案。
タブの分け方の基準として「軸で分ける」を推奨した理由は、
画像版 P5-03 の教訓（1つの画面に複数の性質のものを詰めた）から。

同時に、タブ案の副作用への対策として以下を提案していた。
- 状態サマリー（各タブの状態を常時表示）
- 一括操作
- 矛盾の警告

### hirosof の指摘と代案

> 流石に7タブは多いですね。

draw.io で作成した UI 案を提示。
縦に並んだカード一覧を主画面とし、各カードの「変更」ボタンで設定画面を開く。
最下部に「以上の設定を元にチャット系AIに渡すプロンプトを作成する」ボタン。

補足として:
- 変更ボタン → 別画面かポップアップ。6件とも揃えたほうが良い
- プロンプト作成ボタン → 「ボタンの下」「別画面」「ポップアップ」のいずれか

### 採用理由

この案のほうが優れている。特に**状態サマリーが不要になる**点が大きい。
タブ案では全体が見渡せないため追加要素が必要だったが、
一覧画面そのものがサマリーになるため、設計要素が1つ減る。

詳細は `decisions/ui-and-nonfunctional.md` §1。

### 決めたこと

| 論点 | 決定 | 決め手 |
|---|---|---|
| 別画面 / ポップアップ | **ポップアップ**（6件統一） | 一覧のスクロール位置が保たれる |
| ポップアップの確定方法 | 即時反映 | 自動保存との状態のずれを防ぐ |
| 依頼文の表示場所 | ボタンの下 | 生成→確認→修正→再生成 が1画面で完結 |
| 依頼文の更新 | 設定変更で自動更新 | 古い依頼文をコピーする事故を防ぐ |
| カードの表示内容 | 全項目を表示。②お任せも省略しない | RP-02 の「指定なし表記の廃止」の実装 |

元の UI 案になかった要素として、保存・読み込みと対象ツール表示を画面上部に追加。

## 2. hirosof からの3つの着想

### 2-1. 保存機能の具体化（→ R-05）

> 設定項目が多いので設定内容をファイルとして保存できる機能があってもいい。
> ブラウザ上にプロファイルとして保存できる機能も併せてあると便利。
> プロファイルについては、バックアップを兼ねて複数のプロファイルを
> エクスポート・インポートできる機能もあった方がいい。

→ 保存を3種類に整理した。

| 種類 | 保存先 | 目的 | 個数 |
|---|---|---|---|
| 自動保存 | localStorage | 作業中の状態を保つ | 1 |
| 設定プロファイル | localStorage | 設定に名前を付けて残す | 複数 |
| ファイル | ダウンロード / 読み込み | バックアップ、他環境への移動 | 任意 |

決めたこと:
- エクスポートは**単一プロファイルと全プロファイル一括の両方**
- `exportType` フィールドで単一と一括を同じ読み込み処理で扱う
- **インポート時は「追加」か「置換」かを選べる**
  （バックアップ復元と設定の取り込みで必要な動作が違うため）

用語の衝突を解消:
「プロファイル」が R-10 の「ツールプロファイル」と衝突するため、
**設定プロファイル**（ユーザーの入力内容）と
**ツールプロファイル**（Suno の仕様定義）で呼び分けることにした。

### 2-2. 3値選択【設計上の欠陥の指摘】

> 例えば「特定の楽器を使用しない」とかはどう指定しようかな。
> 「使用楽器」と「未使用楽器」を指定できる個所を別に作るより、
> 両方一か所で指定できるようにして、
> 「使用する」「使用しない」「未指定（未選択）」の3値選択式の方がよさそう。
> 別につくると、矛盾した選択が選択できてしまう問題が発生してしまう。

**これはこれまでの設計の欠陥だった。**

当初の設計では、楽器はグループ4に指定し、除外はグループ7に書く形だった。
この構造だと同じ楽器を使用と除外の両方に指定できてしまう。
RP-04 の「除外優先」はこの矛盾を**事後的に**解決するルールだったが、
**そもそも矛盾を入力できない構造にするほうが正しい**。

#### 変更内容

- 選択肢を持つ項目のうち、除外があり得るものを3値選択に変更
  （主旋律/伴奏/リズムの楽器、基調となる情緒、副ジャンル、地域・文化の様式）
- 排他的な選択（強度、明暗、テンポ感、編成の規模、質感系、声の扱い）は対象外
- **グループ7（除外）の役割が変わった**:
  「除外したい要素をすべて書く」→「プリセットの選択肢にない除外だけを自由記述で書く」

#### 波及した変更

| 対象 | 変更 |
|---|---|
| 矛盾の警告 | 「使用する要素と除外する要素の重複」の警告が**不要になった** |
| RP-04 の除外優先 | **自由記述との矛盾に対してのみ適用**される形に縮小 |
| 依頼文のセクション6 | 3値選択項目は「使用する」「使用しない」の列で表現 |
| データ構造 | 項目の `state` と選択肢ごとの3値を**別の層**として持つ |

#### 未指定と②お任せの関係（整理が必要だった点）

3値の「未指定」は個々の選択肢に対する状態で、項目全体の状態とは別の層。

- 項目が②お任せ: 選択肢に何も触れていない
- 項目が①指定で、ある選択肢が未指定: 他は指定したが、この楽器については何も言っていない

### 2-3. 曲名案の複数出力（→ R-14）

> 同一のプロンプトで複数の曲を作成する可能性があるので、
> 曲名案の発行希望数を複数指定できてもいい気がしました。

→ 「曲名案を出させるか」に**希望数**（既定3）を追加。

論点: プロンプトの案の数と曲名案の数の関係。

| 案 | 内容 |
|---|---|
| A | プロンプトの案ごとに曲名案を出す（3案 × 3曲名 = 9個） |
| **B ← 採用** | プロンプト全体に対してまとめて出す（3個） |

B を採る理由は、指摘された前提そのもの。
曲名は**同じプロンプトから生まれる複数の曲に付けるもの**で、プロンプトの案とは独立している。
回答フォーマットでは、曲名案を案ごとの出力ではなく末尾にまとめて置く。

ただしプロンプトの案ごとに曲の性格が変わる場合、曲名も変わるべきという考え方もあり得るため、
既定は B とし、必要なら後から選択式にできるようにしておく。
