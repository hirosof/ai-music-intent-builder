## 1. 入力項目の洗い出し

### 方針

画像版 P5-01（テーマとジャンルの軸が混在し、後から分離とマイグレーションが必要になった）
の教訓から、**先に軸を定義し、それから項目を配置する**順で進めた。

### 軸の定義（6軸）

A 用途・文脈 / B ジャンル・様式 / C 情緒・雰囲気 / D 音の構成 /
E 時間的な構造 / F 制作・質感

画像版の5軸（用途、ジャンル、雰囲気、要素、画風）に、
音楽固有の「時間的な構造」を加えた構成。

指摘した注意点:
- B と C は混ざりやすい（「エピック」はジャンルとも情緒ともとれる）
- A は他の軸を導出する根拠になり、②お任せの補完時の主な手がかりになる。
  ただしこれはデータ構造の階層を意味しない

### 項目の配置

グループ1〜8 に約28項目、グループ9（出力の制御）に7項目。
詳細は `decisions/input-items.md`。

## 2. 値の状態の定義（DP-01）

画像版で Phase 4 として後付けされた部分を、ここで先に済ませた。

各項目について次の3つを定義:
1. どの状態を取り得るか（①②③④）
2. ②お任せのとき、何を手がかりに決めるか
3. ①指定のとき、どこまで具体化してよいか

3つ目が画像版で曖昧だった部分。
「和風」という指定に対して尺八と太鼓を足すのは具体化なのか勝手な追加なのか。

### 具体化の3分類を新設

拡張可 / 翻案可 / 保持。共通の語彙として先に定義した。
この分類は想定するバリエーション（Suno 側の書き換え）とは独立。

### 定義作業から導かれた新しい原則

| ID | 原則 | きっかけ |
|---|---|---|
| RP-10 | 軸をまたぐ拡張の書き先 | 「和風」→尺八・太鼓 の拡張結果をどこに書くかが未定義だった。決めないと同じ内容が複数箇所に現れ、文字数を無駄に消費する |
| RP-11 | ②お任せの既定は「足さない」 | 「お任せ」を「必ず何か決めさせる」と解釈すると、指定していない要素が勝手に増える |

### ③の定義を広げた

RP-02 では③を「ツール既定」としていたが、
強度（中程度）・明暗（中間）など**本ツール側の既定値**も必要になった。

→ ③を「**既定値に従う**（ツールまたは本ツールの既定値）」に広げた。
どちらも「値がわかっている」点で同じ扱い。

## 3. 出力形式の確定

### 歌詞欄を出力対象から外す

依頼文に「歌詞欄は空にせよ」と書くのではなく、**そもそも出力対象から外す**。
「空にせよ」と書くと、チャットAI が空のコードブロックを出したり
構成タグを書き込んだりする余地が生まれるため。

### 3つの論点

1. **補完一覧は案ごとか全体か** → 折衷（共通部分を全体の一覧に、案ごとの差は「狙い」に）
2. **コードブロックの入れ子** → 依頼文の中に回答例を含めない
3. **案ごとの差の付け方** → 入力項目（グループ9）に追加。既定は「お任せ」

3つ目から RP-12（案の間で変えてよい範囲）を新設。

### セクション5・6 の書式

- セクション5 に「**本文に書かないこと**」の表を明示的に置く → RP-05 の実装。
  画像版では「解像度はプロンプトに含めない」が文章に埋もれていた
- セクション6 を**表形式**にする → 状態と値が常に対で現れるため。
  散文だと状態の表記が省略されやすく RP-02 が形骸化する

## 4. hirosof からの2つの着想

### 4-1. 基本プロンプト（→ R-17）

> バリエーションがオフ以外だと、Suno 側で変更される可能性がある。
> なので、Suno 側で変更される前提のプロンプト（必要最低限の短めのプロンプトを含む）が
> AI に発行されても良い気がした。

これまでは「想定するバリエーションによってチャットAI の書き方を変える」設計だった（R-12）。
この着想はそれを一歩進め、**成果物そのものを複数の粒度で出させる**もの。

→ 以下を**独立した2本の軸**として扱うことに。
- 粒度の軸: 基本プロンプト / 詳細プロンプト
- 設定の軸: 想定するバリエーションの値

利点: 両方を出させれば Suno 側で組み合わせを生成時に選べる。
**依頼文を出し直さずに試行錯誤できる**。

副次的効果:
- 実例5-1 と同じ比較が自分でできるようになり、H-01 / H-03 の検証に使える（→ H-07 を追加）
- チャットAI に「何が核か」を明示させることになり、
  RP-06 の「重要な要素を先頭に置く」をより確実に守らせる仕組みになる

注意: 「両方」にすると出力量が倍近くになる。
3案 × 2粒度 × 2言語では長くなりすぎる可能性 → Q-13 として記録。運用しながら調整。

### 4-2. 出力言語の選択肢（→ R-08 の書き換え）

> Suno は日本語のスタイルが理解できるので、すべて日本語で生成されるバージョンも有り。
> 「すべて英語」「すべて日本語」「標準（英語・日本語混在）」のような選択肢があっても良い。
> ※ 歌詞生成用のプロンプトも日本語解釈可能である

R-08 は「英語を基本、日本固有の語は日本語も許容」という仮説だった。
この仮説の裏返しとして「すべて日本語」も成立するはず。

実際、実例の生成曲2 は **Suno が日本語のみでスタイルを書き換えて**いた。
Suno 自身が日本語で完結したスタイルを生成する以上、日本語のみの入力も機能すると考えるのが自然。

→ R-08 を「ユーザーが選択する3つの選択肢」に書き換え。既定は「標準（混在）」。

→ **優劣は示さない方針**とした。
第三者情報の「英語のほうが認識精度が高い」は対象バージョン v4.5〜v5 期で、v6 では未検証。
UI の説明文には「Suno は日本語も解釈できる」という事実だけを書き、推奨は付けない。

→ RP-08 も書き換え。
「英語の欄には日本語訳を付ける」→「**ユーザーの母語以外で書かれた欄には訳を付ける**」に一般化。
「すべて日本語」を選んだ場合、訳は不要になる。

→ 歌詞の場合は「指示文の言語」と「歌詞本文の言語」が**別の軸**になる点を L-01 に記録。

### 文字数への影響（保留と判断）

日本語は英語より1文字あたりの情報量が多い。
実例では英語中心が約200文字、日本語中心が約90文字。
上限 1,000文字に対してはどちらも余裕があるため、
推奨長の言語別管理は**実害が出るまで保留**とした。

hirosof のコメント:
> AI が発行するプロンプトの言語の密度とかは、実際に運用してから修正していくのが好ましい
