## 1. 画面構成【一覧 + ポップアップ方式】

### 採用案

縦に並んだ**カード一覧を主画面**とし、各カードの「変更」ボタンで
設定用のポップアップを開く。一覧の最下部に依頼文の生成ボタンを置く。

```
┌───────────────────────────────────────┐
│ [対象ツール: Suno v6]        [保存] [読込] [プロファイル] │
├───────────────────────────────────────┤
│ ┌─────────────────────────────────┐ │
│ │ 基本                    指定4/お任せ3  [変更] │ │
│ ├─────────────────────────────────┤ │
│ │ 用途          ゲームのボス戦BGM            │ │
│ │ 用途の詳細     お任せ                     │ │
│ │ 主ジャンル     オーケストラ                 │ │
│ │ 副ジャンル     お任せ（追加しない）          │ │
│ │ 地域・様式     和風                       │ │
│ │ 年代・時代感    お任せ                     │ │
│ │ 聴取環境      ループ再生する                │ │
│ └─────────────────────────────────┘ │
│ （表現 / 音の構成 / 構造 / 除外・補足 / 出力設定 も同様）   │
│                                           │
│ [ 以上の設定を元にチャット系AIに渡すプロンプトを作成する ]    │
│                                           │
│ （生成された依頼文をここに表示）                    │
└───────────────────────────────────────┘
```

### タブ案を採らなかった理由

当初は軸ごとの7タブ構成を検討したが、一覧方式のほうが優れている。

| # | 理由 |
|---|---|
| 1 | **状態サマリーが不要になる。** タブ案では全体が見渡せないため「各タブの状態を常時表示するサマリー」という追加要素が必要だった。一覧画面そのものがサマリーになるため、設計要素が1つ減る |
| 2 | **入力と確認の位置づけが分かれる。** タブは「同格の画面が7枚」だが、一覧方式は「一覧が主、設定は従」。約28項目を扱うツールでは「戻る場所がある」構造が効く |
| 3 | **依頼文の構成と対応する。** 依頼文のセクション6も軸ごとの表。一覧の並びがそのまま依頼文の構造に対応する |
| 4 | **グループをまたぐ警告の置き場所ができる。** タブ案では「どのタブに出すか」が曖昧だった |

### カードの構成

| カード | 内容 | 対応する軸・グループ |
|---|---|---|
| 基本 | 用途・文脈、ジャンル・様式 | 軸A、B |
| 表現 | 情緒・雰囲気、制作・質感 | 軸C、F |
| 音の構成 | 楽器、声、編成 | 軸D |
| 構造 | 長さ、テンポ、展開、構成 | 軸E |
| 除外・補足 | 除外（自由記述）、その他 | グループ7、8 |
| 出力設定 | 案の数、粒度、言語、バリエーション、曲名、パラメータ | グループ9 |

軸C と F を1カードにまとめたのは、どちらも「聴こえ方の印象」に関わり項目数も少ないため。
ただしカード内・ポップアップ内では見出しで分け、**データ上も別の軸として保持する**。

### カードに表示する内容

- **②お任せの項目も省略せずに表示する。**
  これが RP-02 の「指定なし表記の廃止」の実装。
  項目を省略すると「指定していない」状態が見えなくなり、状態区分の意味がなくなる
- **状態を視覚的に区別する。** ①指定は通常の文字、②お任せは淡い文字など
- カードのヘッダーに件数（`指定 4 / お任せ 3`）を添える

### 1-2. 歌あり対応で足すカード（H1。判断ポイント48。2026-10-19）

L-01（歌あり）は、6カードの構成（上の表）より後に決まったため、`vocalMode`・`lyricsAuthor`・`requestScope` と、歌詞の3項目（`lyricsTheme`・`lyricsLanguage`・`lyricsStructure`。軸G）の置き場所がなかった。カードを次の8枚にする（インストのときは7枚）。

| カード | 内容 | 表示条件 |
|---|---|---|
| **曲の種類**（新設。先頭） | ボーカル区分（`vocalMode`）、作詞の主体（`lyricsAuthor`）、依頼文の範囲（`requestScope`） | カードは常に出す。`lyricsAuthor`・`requestScope` は歌ありのときだけ出す |
| 基本 | 用途・文脈、ジャンル・様式 | 常に |
| 表現 | 情緒・雰囲気、制作・質感 | 常に |
| 音の構成 | 楽器、声、編成 | 常に |
| 構造 | 長さ、テンポ、展開、構成（`structure`） | `structure` は、インストのときだけ出す（歌ありは `lyricsStructure` を使う） |
| **歌詞**（新設。構造の次） | `lyricsTheme`・`lyricsLanguage`・`lyricsStructure` | 歌ありのときだけ |
| 除外・補足 | 除外（自由記述）、その他 | 常に |
| 出力設定 | 案の数、粒度、言語、バリエーション、曲名、パラメータ | 常に |

- 「曲の種類」を先頭にした理由: 依頼文の全体を変える設定で、他のカードの意味（歌詞カードの有無、構成の切り替え）が決まるため。`requestScope` はデータ上は `output` の項目（`input-items.md` 判断ポイント28）だが、出力設定ではなく先頭に置く
- 「曲の種類」カードは、件数（`指定 n / お任せ n`）を出さない（状態を持つ項目ではない）
- 歌ありに切り替えたとき、`lyricsAuthor` は未選択のまま（①指定必須で既定値を持たない。`input-items.md` 判断ポイント20）。未完成として示す（判断ポイント43）
- `structure` と `lyricsStructure` の切り替え、インスト↔歌ありの切り替えで消える項目の値は、画面上は一時保持する（判断ポイント30）。保存データには入れない（判断ポイント45）
- `requestScope` により依頼文に出ない項目は、淡く表示するが、編集は妨げず、値は保持する（出力条件は `../specifications/request-blocks.md` §3-4）。表示の細部は U4 で決め、判断ポイントに記録する → **判断ポイント53（U4a で決定）**
- カードの開き方は、新設の2枚も含めて同じ（ポップアップ。判断ポイント1・38）

## 2. ポップアップ

### 別画面ではなくポップアップ（モーダル）

| 観点 | ポップアップ | 別画面 |
|---|---|---|
| 一覧への復帰 | 閉じるだけ。**スクロール位置が保たれる** | 遷移が必要。位置の復元に実装が要る |
| 実装 | ルーティング不要 | ルーティングが必要 |
| 項目数が多いとき | スクロールが必要 | 広く使える |

決め手は**スクロール位置の保持**。一覧が縦に長いため、
設定から戻ったときに先頭に飛ばされると使いにくい。

**6カードすべてで方式を統一する**（片方が別画面、片方がポップアップだと操作の予測が立たない）。

項目数が多いカード（基本7項目、音の構成5項目）は、ポップアップ内で小見出しに分ける。

### 選択肢の選ばせ方

ジャンルや楽器のように選択肢が多く階層を持つ項目は、
**ポップアップ内に階層テーブルを置く**（オーバーレイを重ねない）。
選択肢が少数の択一項目は、ボタン群（SelectButton 相当）か Select を使う。

詳細は `presets.md` §4。本文書 §2 の「6カードすべてで方式を統一する」は
**カードの開き方に関する規則**であり、
ポップアップ内で項目の性質に応じてコンポーネントを使い分けることは妨げない。

### 即時反映

| 案 | 内容 |
|---|---|
| **即時反映 ← 採用** | 変更がすぐ一覧に反映される。閉じるボタンのみ |
| OK / キャンセル | 確定するまで反映されない |

即時反映を採る理由: このツールは**入力途中の状態を自動保存する**（§4-1）ため。
OK / キャンセル方式だと「キャンセルしたのに自動保存されていた」という状態のずれが起きる。

### 2-2. ポップアップ内の大きな入力欄の畳み方（判断ポイント54。2026-10-20）

初版の実装後、「基本」カードのポップアップが長いと分かった（主ジャンル・副ジャンル・地域・文化の様式の3つの階層テーブルが、お任せのときも開いたまま）。入力欄が大きい項目は、**状態が①指定のときだけ開き、それ以外は畳む。**

| 項目 | 規則 |
|---|---|
| 対象 | 入力欄が大きい項目: 階層テーブルを持つ項目（主ジャンル・副ジャンル・地域・文化の様式・基調となる情緒・楽器の統合テーブル）と、その自由記述の入力欄。ボタン群・1行の入力など小さいものは、従来どおり「①以外は入力欄を無効化する」（判断ポイント28） |
| 畳むとき | 状態が②お任せ・③既定値・④ツール任せのとき。表・検索・「非表示の語も表示」・自由記述を隠し、状態のトグル（または選択肢のグループ）と、「一覧を開く」ボタンだけを出す |
| 開くとき | ①指定のとき。値が空のまま①指定にした未完成のとき（S5）も開く（入力欄と警告を見せるため） |
| 「一覧を開く」ボタン | 状態とは独立に、表を開閉する。`select` 種の項目（主ジャンルなど）は、表で値を選ぶことそのものが指定で、畳むと選べなくなるため、このボタンが入口になる。開いて値を選んだら①指定になり、開いたままになる。開いても選ばないまま畳んだ場合は、状態は変わらない。`triSelect` 種は、「指定」を押すと開く |
| 値の保持 | 畳んでいる間も、画面上の値は一時保持する（①に戻すと復元。判断ポイント30）。保存データには入れない（判断ポイント45） |
| カードの一覧 | 変更なし（②お任せも省略せず表示する。§1） |

- 「①以外は入力欄を無効化する」（判断ポイント28）は、入力欄が大きい項目では「畳む」に改める。無効化のまま表示し続けると、お任せを中心に使う普通の場合でもポップアップが長くなるため
- 指定が多いときは、まだ長くなる。その場合の対策（項目ごとのアコーディオン、カードの分割）は、使ってみてから検討する（採らなかった案として記録）
- 統合テーブル（楽器の3項目。判断ポイント31）は、3項目のいずれかが①指定のときに開き、すべてが②お任せのときだけ畳む（補完。細部は U4/U5 で直しやすい形にしてよい）

## 3. 依頼文の表示

### 表示場所: ボタンの下

| 案 | 評価 |
|---|---|
| **ボタンの下 ← 採用** | 生成→確認→上に戻って修正→再生成 が1画面で完結する |
| ポップアップ | 依頼文を見ながら一覧の内容を確認できない |
| 別画面 | 修正のたびに往復が必要 |

- **生成後は自動でその位置までスクロールする。** 一覧が長いため、画面外だと気づけない **→ 2026-10-20 に判断ポイント55 で廃止（§3-1）**
- **設定変更に応じて自動更新する。**
  「変更したのに古い依頼文をコピーしてしまう」事故を防ぐため。
  ボタンは「生成」ではなく「依頼文を表示する（位置へスクロールする）」という位置づけになる **→ 2026-10-20 に判断ポイント55 でボタンを廃止（§3-1。この節の「ボタンの下」は「一覧の下」と読む）**

### 3-1. 依頼文の表示の形（「以上の設定を元に…表示する」ボタンの廃止。判断ポイント55。2026-10-20）

初版の実装後、一覧の最下部の「以上の設定を元にチャット系AIに渡す依頼文を表示する」ボタンの存在意義が薄いと分かった（利用者の気づき）。依頼文は設定の変更に応じて自動で更新され（判断ポイント3）、ボタンの役目は「依頼文の位置へスクロールする」だけになっていたが、出力設定カードの直下に依頼文が出ているため、押さなくても結果が見える。

| 項目 | 決定 |
|---|---|
| ボタン | **廃止する。** 依頼文は常に表示し、設定の変更で自動更新する（判断ポイント3。この節の「ボタンの下」は「一覧の下」と読む）。§1 の図の「[ 以上の設定を元に… ]」も同じ |
| 形 | 依頼文の表示を、**他のカードと同じ形（枠・見出し行）**にする。見出し行に「依頼文」と「コピー」を置き、カード一覧の最後のカード（出力設定）との間に、他のカード間より少し広い余白を取る（ボタンが担っていた区切りの役目を、カードの形と余白で補う） |
| 未完成のとき | 未完成（S5・F12。判断ポイント43）のデータでは、依頼文を生成しない。依頼文のカードの中に理由（「指定されていますが値が空です」「歌ありで作詞の主体が未選択です」など）を示す。「コピー」は無効にする |
| 注意書き | §3-2・§3-3 の注意書きは、依頼文のカードの中（依頼文とコピーボタンの下）に置く。順序は従来どおり（§3-3 を先に、§3-2 をその下に） |
| スクロール | ボタンが担っていた「生成後に位置までスクロールする」は廃止する。依頼文が画面の外にあるときに「依頼文へ ↓」を出す浮動ボタンは、採らなかった案として記録（スマホ幅で不便が出たら追加を検討） |

### 3-2. ツール固有の注意書き: 作詞AIへの指示のチップ化（宿題42。2026-10-18。仕様のみ → 2026-10-20 に U5 で実装）

Suno の作詞AIへの指示欄は、貼り付けが241文字以上だと入力欄ではなく添付チップになり、チップだけでは送信できない（`../research/suno-profile.md` §5-3。240文字までは入力欄に入る）。対応は案D：**依頼文は変えず**、UI で一言を案内する。

| 項目 | 内容 |
|---|---|
| 出す条件 | 次の**すべて**を満たすとき。①対象ツールが Suno、②`vocalMode = vocal`、③`lyricsAuthor = chat-ai-instruction`、④`requestScope` が `combined` または `lyrics`（②〜④は、依頼文に「作詞AIへの指示」の欄が出る条件〔`../specifications/request-blocks.md` §3-3 の 5-1〕と同じ）。条件を外れたら出さない |
| 常に出す理由 | チャットAIが書く指示文の長さを、このツールは事前に知れない。240文字以内に収まる回答もあるため、「チップになったとき」に読む注意書きとして、条件を満たす間は出し続ける |
| 置き場所 | §3 の依頼文表示エリア。依頼文とコピーボタンの**下**。依頼文の本文には含めない |
| 形 | 小さな注意書き1つ（Nuxt UI の `UAlert`、情報色）。閉じるボタンは付けない。閉じた状態は保存しない（UI 設定〔§4-6〕を増やさない） |
| 一言のコピー | 一言の横に専用のコピーボタンを置く。実装は判断ポイント33と同じ（`useClipboard`、`legacy: true`）。ラベルの切り替えも同じ |
| 一言 | 「添付のテーマ・指示に従い歌詞を作成してください」（実機で歌詞が生成された文。固定） |
| データの持たせ方 | 初版は UI の定数（文面・閾値240・一言）。ツールプロファイルへの属性追加は、他のツールにも同種の案内が必要になった段階で検討（判断ポイント41）。`suno.json` の `lyrics-prompt` の `note` は現状のまま |

文面（利用者向け。内部の参照は書かない）:

```
Suno の「作詞AIへの指示」欄に貼るとき
チャットAIが書いた指示文が241文字以上だと、Suno の入力欄では本文ではなく添付（チップ）になり、そのままでは送信できません。
チップになったときは、入力欄に次の一言を添えて送信してください。
  添付のテーマ・指示に従い歌詞を作成してください    [コピー]
240文字までなら、そのまま貼って送信できます。この一言で指示がどの程度歌詞に反映されるかは、まだ確認できていません。
```

- 「241文字」は 2026-10-17 の1回の観察（アカウント・画面幅・時期による差は未確認）。文面は断定を避け、閾値が変わったら §3-2 の定数と文面を直す
- `style` では出さない（作詞AIへの指示が依頼文に出ないため）。`chat-ai`（Claude が歌詞を書く）でも出さない（指示欄を使わないため）

### 3-3. 文字数超過の注意書き（宿題50。2026-10-19。仕様のみ → 2026-10-20 に U5 で実装）

チャットAI が書いたスタイル欄が、Suno の上限（1000文字）を超えることがある（254案中7案＝2.8％。現行のモデルでは ChatGPT のみ（14％）。最大 +234）。Suno は貼り付けたときに**末尾を切る**（2026-10-19 に利用者が確認。`../specifications/tool-profiles/suno.json` の `note`）。対応は、依頼文を変えず、UI で一言を案内する（宿題50の (a)）。根拠と測定は `../examples/rendered-13-new-instrumental-freetext-all-english.md` §6-4。

| 項目 | 内容 |
|---|---|
| 出す条件 | 次の**すべて**を満たすとき。①対象ツールが Suno、②`requestScope` が `combined` または `style`（依頼文にスタイル欄が出る条件。`../specifications/request-blocks.md` §3-3 の 5-1）。条件を外れたら出さない |
| 常に出す理由 | チャットAI の回答の長さを、このツールは事前に知れない。超過するかは回答しだいで、条件を満たす間は出し続ける |
| 置き場所 | §3 の依頼文表示エリア。依頼文とコピーボタンの**下**。§3-2 の注意書きがあるときは、この注意書きを先に、§3-2 をその下に置く。依頼文の本文には含めない |
| 形 | 小さな注意書き1つ（Nuxt UI の `UAlert`、情報色）。閉じるボタンは付けない。閉じた状態は保存しない（UI 設定を増やさない。§4-6） |
| 上限の値 | ツールプロファイルのスタイル欄の `limit.value` を使う（文面に直書きしない） |
| 基本プロンプトの案内 | 出力の粒度（`output.granularity`）に基本プロンプトが含まれるときだけ、「長すぎるときは基本プロンプトを使えます」の一文を添える（基本プロンプトは、数語が30語程度で、上限を超えない。利用者の見解、2026-10-19） |
| データの持たせ方 | 初版は UI の定数（文面）。ツールプロファイルへの属性追加、スキーマ・チェッカーの変更はしない |

文面（利用者向け。内部の参照は書かない。`{上限}` は `limit.value`）:

```
Suno のスタイル欄は{上限}文字までです。
AI の回答が上限を超えていると、貼り付けたときに末尾が切れます。貼る前に文字数を確認してください。
（基本プロンプトを出力しているとき）詳細プロンプトが長すぎるときは、基本プロンプトを使えます。
```

- この注意書きは「超過に気づく手段」ではない（文字数カウンタは作らない。`scope.md` §16。利用者の見解、本ツール側で作っても意味が薄い）。文字数の確認は、利用者が Suno の入力欄で行う（依頼文 5-1 の「文字数の確認は私の側で行います」と同じ）
- 「除外」欄も上限は同じ（1000文字）だが、実測で超過が見られたのはスタイル欄の詳細プロンプトだけ（除外欄は41〜44文字）。文面はスタイル欄だけについて書く

## 4. 保存（R-05）

保存を区別する。楽曲の内容に関わる3種類に加え、画面の見え方の設定（UI 設定）を別に持つ。

データの全体の形（楽曲データ、プロファイル、エクスポートファイル、UI 設定）は `../specifications/song-file.md` にある（判断ポイント10〜22。2026-09-21）。本節は決定と理由。

| 種類 | 保存先 | 目的 | 個数 |
|---|---|---|---|
| 自動保存 | localStorage | 作業中の状態を保つ | 1（現在の編集内容） |
| **ユーザープロファイル**（旧・設定プロファイル） | localStorage | 設定に名前を付けて残す | 複数 |
| ファイル | ダウンロード / 読み込み | バックアップ、他環境への移動 | 任意 |
| UI 設定 | localStorage（別のキー） | 語ごとの表示の有無など、画面の見え方 | 1 |

### 用語の区別

「プロファイル」は R-10 の「ツールプロファイル」と語が衝突するため、呼び分ける。

- **ユーザープロファイル**（旧・設定プロファイル）: 利用者が名前を付けて保存する入力内容。プロジェクトファイルに近い（判断ポイント18）
- **ファクトリープロファイル**: アプリに同梱する入力内容の見本。書き換えられない。利用者の保存ではないため、保存の種類には数えない（`song-file.md` §4-4。判断ポイント19）
- **ツールプロファイル**: Suno などの仕様定義（R-10）

### 4-1. 自動保存

- ブラウザを閉じても入力が残るようにする（項目数が多く、中断の可能性が高いため）
- localStorage に楽曲データ（`schemaVersion` を含む）を保存する。バージョンが不一致のとき、**移行できれば移行し、移行できなければ破棄する**
  - 2026-09-21 に「不一致なら破棄」から精密化した。理由: 自動保存の目的は作業の保全であり、GitHub Pages への配備で、利用者の操作なしに版が上がりうるため。初版は移行が存在せず、動作は同じ（`song-file.md` §6-3）
- 明示的な操作なしに上書きされる。ユーザープロファイルとは別物

### 4-2. ユーザープロファイル（旧・設定プロファイル）

- 名前を付けて複数保存できる
- 一覧から読み込み・上書き・削除できる
- 1件は `{ name, updatedAt, data }`。`data` は楽曲データそのもの（§4-4）。名前は一意。localStorage の1つのキーに、`{ schemaVersion, profiles[] }` として持つ（`song-file.md` §4）

### 4-3. ファイル入出力

**エクスポートは単一プロファイルと全プロファイル一括の両方**を用意する。
前者は個別の共有や移動、後者はバックアップ用。

```json
{
  "schemaVersion": 1,
  "exportType": "profiles",
  "exportedAt": "2026-09-12T...",
  "profiles": [
    { "name": "和風戦闘BGM", "updatedAt": "...", "data": <楽曲データ（§4-4）> }
  ]
}
```

- 単一は `profiles` が1要素、一括は N 要素。**同じ読み込み処理で扱える**。書き出すファイルは常にこの形で、素の楽曲データがファイルになることはない（2026-09-21。`song-file.md` §4-2）
- `exportType` は内容の種類で、単一と一括の区別ではない（現状は `profiles` のみ。UI 設定などを書き出す必要が出たら、値を足す。§4-6）
- **インポート時は「追加」か「置換」かを選べる。**
  バックアップからの復元と、他環境の設定の取り込みで必要な動作が違うため

実装手段: 読み込み（ファイル選択）は VueUse の `useFileDialog`（標準の `<input type="file">` のラッパー。全ブラウザ対応）を使う。VueUse の `useFileSystemAccess`（File System Access APIのラッパー。同一ファイルへの上書き保存が可能）は**採用しない**。理由: (1) Chromium系（Chrome/Edge/Opera）のみ対応でFirefox・Safariが使えず、VueUse側も自動フォールバックを持たない。(2) 現行設計は「書き出しは常にダウンロード、読み込みは選択して読み込む」で、同一ファイルへの上書き保存を使う場面がない（`discussions/2026-09/17_ui-spec.md`）

### 4-4. データ形式

```json
{
  "schemaVersion": 1,
  "requests": [
    {
      "id": "r1",
      "toolId": "suno",
      "toolVersion": "v6",
      "generationType": "new",
      "vocalMode": "instrumental",
      "lyricsAuthor": null,
      "derivedFrom": null,
      "axes": {
        "purpose": { "state": "specified", "value": "..." },
        "leadInstruments": {
          "state": "specified",
          "choices": { "shakuhachi": "use", "taiko": "use", "guitar": "exclude" },
          "freeText": "..."
        }
      },
      "output": { "variantCount": 3, "granularity": ["basic", "detailed"] }
    }
  ]
}
```

| 要点 | 理由 |
|---|---|
| 各項目を `state` と、種類ごとの値（`value`／`choices`／`freeText`）で持つ（`../specifications/input-items.md` §5。状態名は `specified`／`delegated`／`defaulted`／`toolManaged`） | RP-02 をデータ構造に反映。state を別に持たないと、空文字列が①指定の空なのか②お任せなのか区別できない |
| `schemaVersion` を初版から持つ | 画像版 Phase 5 の教訓 |
| 初版で使わないフィールドも定義する | `lyricsAuthor` / `derivedFrom` は初版では null。後から足すとマイグレーションが必要になる（R-02 で確保すると決めた軸）。派生生成の操作種別（R-02）は `derivedFrom` の中（`{ requestId, operation }`）に持つ（判断ポイント12） |
| `toolVersion` を保存する | 後で開いたとき Suno のバージョンが変わっていれば上限値などが変わっている可能性がある。読み込み時に差異を警告できる |

2026-09-21 に、楽曲データを `{ schemaVersion, requests[] }` の形にした（判断ポイント10）。§4-5 の「要素が1つの配列」と、上の単一オブジェクトの例の食い違いを解消したもの。`toolId`・`toolVersion`・`generationType`・`vocalMode`・`lyricsAuthor`・`derivedFrom`・`axes`・`output` は、段階ごとに変わりうるため要素（依頼）側に置く。`schemaVersion` は楽曲データの最上位。全体の形と検証は `../specifications/song-file.md`。

### 4-5. 保存の単位

DP-05 で「1つの楽曲に複数の依頼文がある」と決めたことへの対応。

| 案 | 内容 |
|---|---|
| 依頼文ごとに1ファイル | 単純。ただし派生元との関係がファイル名頼りになる |
| **楽曲ごとに1ファイル ← 採用** | 新規生成と派生生成を1ファイルに含め、`derivedFrom` で関係を表す |

初版では派生生成を実装しないが、**ファイル形式は楽曲単位で定義しておく**。
楽曲データは `requests` の配列で、初版は要素が1つ。要素どうしの関係は `derivedFrom` で表す（§4-4）。

**2026-10-18 確定**: 初版は新規生成のみ（`scope.md` L-01b。F6 維持）。第2段階で派生生成を足すときに、UI の設計が要るもの: 派生元のカード（`source`、元曲の選択、操作、元のスタイルの扱い、`originalLength`）、複数の依頼の切替・追加、`internal` の元曲の参照（`../handoff-next-thread.md` 宿題48）。

### 4-6. UI 設定

楽曲の内容ではない、画面の見え方の設定。現時点では**語ごとの表示の有無**（`presets.md` §11、R-19）のみ。

- 楽曲ファイル・ユーザープロファイルには含めない。楽曲ファイルの持ち運びが、表示設定に依存しないようにするため
- 表示の有無は、語彙の既定値から変えた `id` だけを、`{ schemaVersion, termVisibility: { 語彙 id: { 語 id: true｜false } } }` の形で持つ（`song-file.md` §5。判断ポイント16）
- `schemaVersion` を持つ。版が不一致なら破棄する（自動保存（§4-1）とは違い、移行は設けない）。不明な id は無視する
- ファイル入出力（§4-3）の対象にするかは未定。初版では対象外とし、必要になったら `exportType` を追加して扱う

### 4-7. U3（保存）の実装前に決めた規則（2026-10-19。判断ポイント43〜47）

Claude Code が U3 の実装前に持ち帰った5件。いずれも、先行する規則（`../specifications/song-file.md` §6・§8・§9）が決めていなかった穴。

**G1. 入力途中の状態の自動保存（判断ポイント43）**

- 問題: 編集途中には、検証がエラーにする状態（S5「①指定なのに値が空」、F12「歌ありで `lyricsAuthor` が未選択」）が普通に起こる。自動保存して復元すると、§6-2 で拒否、§6-3 で破棄となり、作業が丸ごと失われる
- **決定: 保存は厳格、復元は寛容とする。** 自動保存の**読み込みに限り**、S5 と F12（歌ありの未選択。`vocalMode = vocal` で `lyricsAuthor` が `null`）を拒否の理由にしない（「未完成」として読み込み、画面で示す）。この2つ以外のエラー（構造の破綻、不明な id、版の不一致、S6 など）は、従来どおり拒否・破棄（§6-2・§6-3）
- この2つだけを許す理由: 通常の編集で自然に起こる状態だから。他のエラーは、アプリの不具合や版の変更でしか起こらない（S6 は G3 の正規化で保存時に消える）
- **未完成の扱い**: 「未完成」のデータでは、依頼文を生成しない（生成器は明示的に失敗する。`request-blocks.md` §1）。カードで「指定されていますが値が空です」「歌ありで作詞の主体が未選択です」を示す（文面は U4。§5 の警告と同じ置き場所）
- **ユーザープロファイルへの保存とファイルへの書き出しは、エラー0件のときだけ許す**（警告は許す）。ストアに不正なプロファイルが入ると、§6-2 の 5 でストア全体が読めなくなるため。ボタンを無効にし、理由を示す
- 採らなかった案: (b) 有効なときだけ自動保存する（未完成のあいだの編集が失われる）、(c) 保存時に値が空の①指定を省略に落とす（利用者が選んだ状態が変わる）

**G2. ストアが拒否されたときの扱い（判断ポイント44）**

- 問題: localStorage のプロファイルのストアを拒否したあとの動作が決まっていなかった。空として扱って保存すると、既存のプロファイルを上書きして消す
- **決定: 拒否したストアには書き込まない**。プロファイルの保存・削除・取り込みを止め、理由（拒否した理由。版が新しい、不明な id、など）を表示する。自動保存（別のキー）とファクトリープロファイルの読み込みは、使える
- **補足（判断ポイント36 との関係）**: 「書き出す」は、名前を付けてユーザープロファイルとして保存してからエクスポートする。ストアが拒否されているときは、保存が止まるため書き出しも止まってしまう。**ストアが拒否されているときは、名前を付けてファイルにだけ書き出す（ストアには保存しない）。** 作業をファイルとして逃がせる道を残すため
- 採らなかった案: 拒否したストアの生の内容を書き出しられるようにする（拒否は、版の更新や id の削除など開発側の変更で起こる。そのときは移行を追加する（§6-1）のが筋で、機能を足す優先度が低い。必要になったら将来の候補）

**G3. 保存時の正規化（判断ポイント45。判断ポイント30 の「保存データ側の規則」の具体化）**

- **決定**: 保存する楽曲データ（自動保存・プロファイル・書き出しのすべて）は、次の3点を満たすように正規化してから保存する: (1) ①指定以外の項目は値を持たない（`input-items.md` §5 の既存の規則）。(2) 今の `vocalMode` で無効な項目（S6）は省略する（状態に関わらず。判断ポイント61）。(3) インスト（`vocalMode = instrumental`）のとき、`requestScope` は `combined`、`lyricsAuthor` は `null`
- 正規化しないもの: `output` のその他の値（`lyrics` 範囲で使わない値も保持する。`input-items.md` 判断ポイント28 ③）
- 画面上の一時保持（判断ポイント30）は、ブラウザを開き直すと消える。保存データに入れない（インストに切り替えると歌詞の項目の値が保存されないのは、この規則の帰結）

**G4. ファイルの読み込みで受け付ける形（判断ポイント46）**

- **決定**: エクスポートファイル（`exportType: "profiles"`）だけを受け付ける。素の楽曲データ・ストアの形は拒否する（§4-3 の「素の楽曲データはファイルにならない」）。拒否するときは、「エクスポートファイルを使ってください」と理由を示す
- `check_fields.py` の形の自動判別は、検証ツールとしてそのまま残す（アプリの読み込みとは別）

**G5. カラーモードの保存キー（判断ポイント47。判断ポイント32 を改める）**

- 食い違い: 判断ポイント32 は VueUse の既定キー `vueuse-color-scheme`（接頭辞なし）。`../specifications/song-file.md` §8 は「キーには接頭辞を付ける」（`github.io` を他のツールと共有するとキーが衝突する）
- **決定: カラーモードの保存キーにも、アプリの接頭辞を付ける。** 実現は U4（`useColorMode` の `storageKey`）。ただし、Nuxt UI の `ColorModeSelect` が使う `useColorMode` に `storageKey` を渡せるかは未確認。渡せないとわかったときは、**既定キーのままを例外として記録してよい**（衝突しても、ライト／ダークの好みが他のツールと共有されるだけで、楽曲データに影響しない）。このキーは、§8 の3つのキー（自動保存・ストア・UI 設定）とは別の4つ目（VueUse が管理する）。UI 設定には含めない（判断ポイント32 のまま）

### 4-8. 「新規」（初期状態に戻す）の操作（H5。判断ポイント52。2026-10-19）

- 問題: 最初からやり直す手段が「ファクトリープロファイルを読み込む」しかなく、初期状態の定義もなかった
- **決定**: ヘッダー（保存・読込・プロファイルの並び）に「新規」を置く。押すと、編集中の内容を**初期状態**に置き換える
- **初期状態**: `toolId` は対象ツール、`toolVersion` はツールプロファイルの版（`version.id`）、`generationType = new`、`vocalMode = instrumental`、`lyricsAuthor = null`、`derivedFrom = null`、`axes` は空（すべて省略。各項目の初期状態＝`fields.json` の `initialState`。`input-items.md` §5 の「省略は初期状態」）、`output` は `fields.json` の出力項目の既定値（案の数3・粒度は基本と詳細・バリエーション標準・出力言語標準・曲名案オフ・`requestScope = combined` など）。`id` は新しく作る（`song-file.md` §2-2）
- **確認ダイアログを出す**: 「編集中の内容は破棄されます」。ユーザープロファイルへの保存は促さない（保存したいときは、利用者が先に保存・書き出しする。ダイアログに一言添える）。取り消し（元に戻す）は設けない
- 「新規」は、画面上の一時保持（判断ポイント30）と自動保存の内容も初期状態にする。UI 設定（語の表示の有無、カラーモード）と、ユーザープロファイルには触れない
- **補完（判断ポイント52。後で直しやすい）**: 編集中の内容を置き換える他の操作（ユーザープロファイル・ファクトリープロファイルの「編集中の内容への読み込み」）も、同じ確認ダイアログを使う。ファイルからの「追加」「置換」（§4-3）は、編集中の内容に触れないため対象外

## 5. 矛盾の警告

RP-04 で優先順位を定義しているが、**依頼文を出す前にユーザーに気づかせる**ほうが確実。

### 置き場所

- **カード上**: そのグループ内で完結する矛盾
- **一覧の上部または生成ボタン付近**: グループをまたぐ矛盾

### 検出する例

- 長さをカスタムで短く指定したのに、構成のセクション数が多い
- テンポ感と BPM が食い違っている
- 自由記述の内容が構造化項目と矛盾している
- 同一項目内で近い系統を複数「使用する」（例: 副ジャンルに J-POP と K-POP）
- カテゴリの代表と、その兄弟を相反する状態にした（例: `ポップス` = 使用しない、`K-POP` = 使用する）

後ろ2件の根拠と検出方法は `presets.md` §5-3。
「近い系統」は同一カテゴリというだけでは判定せず、明示したペアリストで判定する（`presets.md` 判断ポイント22）。

警告にとどめ、生成は止めない（画像版 Phase 3 の入力値検証と同じ扱い）。
表示設定で非表示にした語も、警告の判定の対象にする（`presets.md` §11-3）。

なお、**3値選択の導入（`input-items.md` §1-2）により、
「使用する要素と除外する要素の重複」は入力段階で発生しなくなった**ため、
この種の警告は不要になった。
