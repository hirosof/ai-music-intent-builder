# 上位原則（DP-xx / RP-xx）

- 最終更新: 2026-09-17
- 状態: DP は暫定、RP は実用水準（依頼文を 5 モデル×3回検証。`request-text.md` §10）

---

## 0. 本ドキュメントの範囲

原則を2層に分ける。

- **設計原則（DP）**: ツールの作り方に関する原則。実装時に守るもの
- **依頼文原則（RP）**: 依頼文に書かれ、チャットAI が読むルール

含まないもの: 入力項目（`input-items.md`）、依頼文の書式（`request-format.md`）、
依頼文の文面（`request-text.md`）、選択肢（`presets.md`）、
作詞（L-01）、曲の構成（R-04）。

原則はツールに依存しない形で書き、Suno 固有の値はツールプロファイルから差し込む。

### 設計順序の意図

画像版は「入力項目 → 依頼文 → ルール後付け」の順だった。
音楽版はこれを逆にし、次の順で決める。

1. スコープ確定（R-01〜R-03）← 完了
2. 依頼文の上位原則（本ドキュメント）← 完了
3. 入力項目の洗い出し（`input-items.md`）← 完了（骨格）
4. 出力形式（`request-format.md`）← 完了（骨格）
5. 非機能（保存・配置）と UI 構成（`ui-and-nonfunctional.md`）← 完了
6. 依頼文の文面（`request-text.md`）← 完了・検証済み
7. 選択肢の設計（`presets.md`）← 完了
8. **選択肢の語彙の作成** ← 現在地

上位原則を先に固めておけば、入力項目を追加しても判断ブレ対策を後から足す必要がなくなる。

## 2. 依頼文原則（RP）

### RP-01: 役割と範囲

- チャットAI の役割は、**音楽生成AI の各入力欄に入れるテキストを作ること**とする
- 音楽や音声を生成する機能を持つチャットAI でも、**その機能は起動しない**
  - 画像版の「Gemini 向け: Nano Banana 起動禁止」を全チャットAI 共通のルールとして一般化したもの
- **確認の質問はせず、補完して最後まで出力する。** 判断に迷った点は出力の「注意事項」に書く
  - 1回の依頼で成果物を得る使い方を想定しているため

### RP-02: 値の状態区分【中核】

「指定なし」には**任せる先が複数ある**。すべての入力項目の値を次の4状態のいずれかで表す。

| 状態 | 意味 | チャットAI の扱い | 補完一覧に書くか | 例 |
|---|---|---|---|---|
| ① 指定 | ユーザーが値を決めた | 従う。言い換えや具体化はしてよい | 書かない | スタイルに「和風戦闘BGM」 |
| ② お任せ | チャットAI に決めさせる | 自由に決めてよい | **書く** | テーマが未定 |
| ③ 既定値に従う | 既定値をそのまま使う（値はわかっている） | その値を前提にしてよい。値は依頼文に明記する | 書かない | バリエーション（標準）、強度（中程度） |
| ④ ツール任せ | 生成時にツールが決める（値はわからない） | **その値を前提にした記述をしない** | 書かない | 長さが Auto |

③の「既定値」には2種類ある。どちらも「値がわかっている」点で同じ扱いとする。

- **ツールの既定値**: Suno のバリエーション（標準）、奇抜さ（50%）など
- **本ツールの既定値**: 強度（中程度）、明暗（中間）など、Suno の設定項目ではないもの

付随ルール:

- **UI では「指定なし」という表記を使わない。** 必ず上の4状態のいずれかで表示する
  - 画像版で「指定なし」の意味が項目ごとにぶれた問題を、表記の段階でなくすため
- **ツール側の設定項目にも同じ区分を当てはめる**
  - 例: 奇抜さが②お任せならチャットAI に推奨値を出させ、③ツール既定なら 50% のまま
  - これにより R-12 の「推奨値を出させるか」がこの区分の中で統一的に扱える
- 出力欄を「出力する／しない」（例: 曲名案を出さない）は、値の状態とは**別の属性**として扱う

### RP-03: 補完

- 補完とは、**②お任せの項目についてチャットAI が決めた内容**を指す
- 補完一覧は表形式で出す。列は「項目」「決めた内容」「理由（短く）」（画像版を踏襲）
- 一覧の単位は**項目**とする。①指定の項目の中での具体化・翻案
  （例:「和風」を尺八と太鼓に具体化する）は補完一覧に含めない
- 案ごとに内容が異なる項目は、表には「案ごとに異なる」とだけ書き、
  実際の内容は各案の「狙い」に書かせる（`request-format.md` §4 論点1 の折衷）。
  **表に入れる文字列を指定する**と遵守率が上がる（検証で 1/5 → 5/5）

### RP-04: 優先順位【依頼文の中でここだけで定義する】

矛盾があったときは、上のものを優先する。

1. **禁止事項**（RP-07）
2. **ツールの制約**（欄の有無、文字数上限、UI 設定で確定している値）
3. **ユーザーの指定**（①の状態のもの）
   - 自由記述と構造化された項目が矛盾する場合は、**自由記述を優先**（既定。設定で変更可）
   - 「含める」と「除外」が矛盾する場合は、**除外を優先**（既定。設定で変更可）
4. **派生元との整合**（派生生成の場合のみ）
5. **チャットAI の補完**（②の状態のもの）

「ユーザーの指定」を「派生元との整合」より上にしている理由:
Cover でジャンルの変更を明示的に指示した場合に、その指示が派生元のスタイルに負けないようにするため。

矛盾を解決した場合は、「何と何が矛盾し、どちらを採ったか」を注意事項に書かせる。

### RP-05: 指定経路

- プロファイルで指定経路が「UI設定」の項目は、**欄のテキストには書かない**
- 指定経路が「併用」の項目は、UI 設定と矛盾しない範囲で本文にも書いてよい
- どの項目にどの経路を割り当てるかは、入力項目の議論で項目ごとに決める

由来: 画像版の「解像度とアスペクト比はプロンプトに含めない」ルールの一般化（R-13）。

### RP-06: 欄の書き方

- 欄ごとに、上限と目標値（上限の9割）を示す
- 重要な要素を先頭に置く
- プロファイルに記録された**書き換えの挙動**に応じて書き方を変える
  - Suno の場合: 想定バリエーションが「オフ」なら完成形として書き、
    それ以外なら核となる要素を短く書く
- **文字数の自己申告は求めない**
  - チャットAI の文字数の数え方は不正確で、誤った数字は
    「上限内に収まっている」という誤った安心感を与えるため
  - 文字数の確認は R-16（文字数カウンタ）で扱う

#### スタイルの書き方（Suno / バリエーション「オフ」時のひな形候補）

- 要素の順序: ジャンル・様式 → 声の扱い → テンポ（BPM） → 情緒・雰囲気 → 楽器編成 → 展開 → 質感
  - 前半4つは第三者情報。後半3つは Suno が書き換えたスタイルの骨格から補った
- 複数ジャンルを組み合わせる場合は、主なジャンルを先に書き、
  他を `with` / `meets` 等でつなぐ（第三者情報）
- 楽器の役割（主旋律を担う楽器、伴奏を担う楽器）を明示すると精度が上がる（第三者情報）
- スタイル欄は「あるもの」を書く欄。要素を打ち消す書き方（`no ○○` 等）は使わせない。
  ただし `wordless` のように要素そのものの名前に含まれる語は許容する
- Suno が書き換えたスタイルの共通の骨格
  （テンポ、楽器編成、声、調性や強弱の変化、残響やミックス）を
  「完成したスタイル」のひな形として使える（実例からの推測）

「重要な要素を先頭に」の根拠は、第三者情報に加えて**実測がある**。
H-07 の検証で、短い入力をバリエーション標準で生成した4曲すべてが
入力先頭の `Orchestral` で始まるスタイルに書き換えられた（2026-09-16）。

#### 除外欄の書き方

専用の除外欄を持つツールでは、次の3点を指示する。

- **否定の記号や語を付けない**。欄自体が除外を表すため二重否定になる
  （Suno は内部的にスタイル文末尾の `-語` として扱っている。`../research/suno-profile.md`）
- **挙がっているものは漏らさない**
- **挙がっていないものを足さない・展開しない**。具体化の許容度は「使用する」側にのみ適用する

後ろ2つは**対で書く**。禁止だけを強く書くと、挙がっている項目まで減る逸脱が実際に起きた
（`request-text.md` §10 の G-01）。

### RP-07: 禁止事項（著作権・倫理・規約）

- **実在のアーティスト名、曲名、既存の歌詞を使わない。**
  参考にしたい場合は、特徴（ジャンル、年代、楽器、歌い方）に分解して表現する
- **この理由を依頼文にも書く。** 権利上の理由に加えて、
  **Suno 側で生成を拒否される原因になる**という実務上の理由があるため
- ユーザーの入力にアーティスト名等が含まれていた場合は、無視せず特徴に分解して使い、
  そうしたことを注意事項に書く
- 不適切な内容（暴力、差別、性的な表現など）を含めない（画像版を踏襲）

補足: 他人の歌詞を無断で使うことは Suno の利用規約違反にあたる（Suno 公式ヘルプ）。
また、実在アーティスト名によるスタイル指定は Suno 側で制限されており、
音の特徴を記述するほうが確実。

将来、作詞家（歌詞ペルソナ）機能を扱う場合も、
実在の歌手や既存曲の歌詞をサンプルに使う作詞家の作成には本ツールでは協力しない方針とする。

### RP-08: 言語

- 依頼文とチャットAI の説明は日本語とする
- 各欄の言語は**ユーザーの選択**（すべて英語 / すべて日本語 / 標準）に従う（R-08）
- **ユーザーの母語以外で書かれた欄には訳を付ける**
  - 画像版の「英語の欄には日本語訳を付ける」を一般化したもの。
    「すべて日本語」を選んだ場合、訳は不要になる

### RP-09: 出力の構成

1. **案ごとの出力**（「案 N ／ 総数」と明記）
   - 粒度ごとのコードブロック（基本プロンプト / 詳細プロンプト。R-17）
   - 訳（ユーザーの母語以外の場合のみ）
   - この案の狙い（1〜2文。何を変えた案かを含む）
   - 除外欄・推奨パラメータ（有効な場合）
2. **補完一覧**（表）
3. **注意事項**（矛盾の解決、特徴への分解、確認したかった点）。ない場合は省略
4. **補足**（必要な場合）

上記以外の成果物（ファイルなど）を作らせない。前置きや後書きも不要とする。
検証で、依頼していないファイルを生成し、その中に UI 設定値を転記する例があったため
（`request-text.md` §10 の G-04）。

詳細な書式は `request-format.md` を参照。

### RP-10: 軸をまたぐ拡張の書き先

ある項目の具体化が他の軸に属する内容になる場合、**その内容は本来の軸の欄に書く**。

例: 「和風」（軸B）から尺八と太鼓を導いた場合、それは軸D（音の構成）の内容として書く。
軸B の記述に「和風（尺八と太鼓を含む）」とは書かない。

これがないと同じ内容が複数箇所に現れ、文字数を無駄に消費する。

### RP-11: ②お任せの既定は「足さない」

②お任せのとき、その項目を**指定しないまま残すことが妥当かどうか**を項目ごとに定義する。
妥当な場合は、チャットAI に何かを決めさせるのではなく、指定なしのまま出力させる。

「お任せ」を「必ず何か決めさせる」と解釈すると、指定していない要素が勝手に増える。
該当する項目は `input-items.md` を参照（副ジャンル・地域の様式・BPM・構成・除外・補足）。声の扱いは2026-09-19 に対象から外した（②はAIが決めてよい。既定は③「声を入れない」。`input-items.md` 判断ポイント9）。

### RP-12: 案の間で変えてよい範囲

- ①指定の項目は、どの案でも変更しない
- **除外欄の内容はどの案でも同じにする**（除外は①指定であり、上の規則の対象。
  暗黙のままだと伝わらず、案ごとに除外欄を変える逸脱が起きた）
- ②お任せの項目と、指定項目の具体化の範囲で差を付ける
- 各案の「狙い」に、何を変えた案かを1文で書く

案ごとの差の付け方はユーザーが選択できる（`input-items.md` グループ9）。

## 3. 依頼文の構成イメージ

画像版ではルールが各項目のセクションに分散していた。
音楽版では**ルールを冒頭にまとめ、要件はその後に置く**構成にする。

```
# 音楽生成AI用プロンプト作成依頼
## 1. 依頼の前提（RP-01）
## 2. 値の状態の読み方（RP-02）
## 3. 優先順位（RP-04）
## 4. 禁止事項（RP-07）
## 5. 対象ツールと欄の定義（プロファイルから生成：欄、上限、指定経路、UI設定の値）
## 6. 楽曲の要件（入力項目から生成）
## 7. 派生元の情報（派生生成の場合のみ）
## 8. 出力形式（RP-03、RP-06、RP-08、RP-09）
```

## 4. 未決の判断ポイント

いずれも既定値で進行中。解釈により依頼文の中身が変わる箇所。

| # | 判断 | 既定値 | 根拠 |
|---|---|---|---|
| 1 | UI で「指定なし」表記を廃止する（RP-02） | 廃止する | 画像版で意味がぶれたため |
| 2 | 自由記述優先を既定にする（RP-04） | 自由記述優先 | 画像版のテンプレートで「その他に記載した内容を優先」が既定だった |
| 3 | 除外優先を既定にする（RP-04） | 除外優先 | 除外したものが入るほうが、入れたいものが欠けるより修正の手間が大きい（保守的な既定値） |
| 4 | 補完一覧は項目単位とし、指定項目内の具体化は含めない（RP-03） | 含めない | 一覧が肥大化するのを防ぐため |
| 5 | チャットAI に確認の質問をさせない（RP-01） | させない | 1回の依頼で成果物を得る使い方を想定 |

## 5. 補完・仮定一覧

| 項目 | 補完内容 | 根拠 |
|---|---|---|
| 除外優先 | 「含める」と「除外」の矛盾では除外を優先 | 保守的な既定値（修正の手間の大小） |
| 目標値 | 上限の9割 | 一般的かつ保守的な仮置き。運用しながら調整 |
| 状態区分の適用範囲 | ツール側の設定項目にも適用 | R-12 を統一的に扱うための提案 |
| 番号体系 | DP / RP の2系統 | 画像版の判断ブレ番号（D-01〜D-06）との混同を避けるため |

## 6. 暗黙の前提

- **依頼文1回で成果物を得る使い方**（チャットAI との往復を前提にしない使い方）を想定している。
  往復しながら詰めていく使い方も想定するなら、RP-01 の「確認の質問をさせない」は見直しが必要
- 上位原則は**新規生成と派生生成の両方に共通で適用される**前提で書いた。
  派生生成に固有のルールは、RP-04 の「派生元との整合」以外は派生生成の議論で追加する
