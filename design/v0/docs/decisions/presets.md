# プリセット（選択肢）の設計

- 最終更新: 2026-09-18
- 状態: 暫定
- 関連: `input-items.md`（入力項目）、`request-text.md`（依頼文の文面）、
  `ui-and-nonfunctional.md`（画面構成）、`principles.md`（RP-02 / RP-08）、
  `vocabulary/README.md`（語彙の選定方法・カテゴリの骨格・カテゴリ別の語彙）

---

## 0. 位置づけ

`input-items.md` で定義した各項目に、**あらかじめ選べる選択肢**を用意する。
カスタム入力は併用し、プリセットに無いものはユーザーが自由に追加できる。

本ドキュメントは**選択肢の持ち方と選ばせ方**を決める。
語彙そのもの（どのジャンルを載せるか）は `vocabulary/` で扱う（§10）。

## 1. データ構造

### 1-1. 項目はフラットに持ち、カテゴリはタグとして持つ

```json
{
  "id": "taiko",
  "label": "和太鼓",
  "categories": ["percussion-family", "wagakki-family"],
  "term": { "en": "taiko drums" }
}
```

**木構造では持たない。** 同じ項目が複数のカテゴリに属し得るため
（和太鼓は打楽器でも和楽器でもよい、エレキギターは弦楽器でも電子系でもよい）、
所属を1つに決められない。

木は**描画するときにだけ構築する**（§3）。保存データと選択状態はフラットのまま。

#### 項目のフィールド

| フィールド | 必須 | 内容 | 定義箇所 |
|---|---|---|---|
| `id` | ○ | 保存データのキー。命名は V-08 | §1-2、`vocabulary/README.md` |
| `label` | ○ | UI の表示名。表記は V-06 | §2-5、`vocabulary/README.md` |
| `categories` | ○ | 所属カテゴリの **`id`** の配列 | §1-3 |
| `term` | — | 言語別の表記。曖昧な語のみ | §2 |
| `represents` | — | 代表項目が指すカテゴリの `id` | §5-3 |
| `jpNative` | — | 日本語が正式表記の語 | §2-6 |
| `aliases` | — | 検索用の別名。依頼文には使わない | §4-2 |
| `defaultVisible` | — | 既定で一覧に表示するか。省略時は `true` | §11 |
| `exclusion` | — | 既定で非表示にした理由。`defaultVisible: false` の語にのみ付ける | §11 |

### 1-2. 保存データとの関係

`ui-and-nonfunctional.md` §4-4 の形をそのまま使う。

```json
"leadInstruments": {
  "state": "specified",
  "choices": { "shakuhachi": "use", "taiko": "use", "electric-guitar": "exclude" },
  "freeText": "..."
}
```

`choices` のキーは項目の `id`。**カテゴリは保存データに現れない。**
これにより、カテゴリ構成を後から変えても保存済みのデータが壊れない。

### 1-3. カテゴリ定義

```json
{ "id": "pop-family", "label": "ポップス系", "order": 10 }
```

カテゴリは**表示のためだけに存在する**。`term` を持たず、選択もされない（§3-1）。
検索用の別名 `aliases` は持てる（§11-4）。

項目の `categories` と `represents` は、カテゴリを**ラベルではなく `id` で参照する**（判断ポイント19）。
ラベルを変えてもプリセット定義と保存データ（§1-2）が壊れないようにするため。

## 2. 表記（`term`）

### 2-1. なぜ必要か

日本語のラベル1つに対し、英語表現が複数あり、**結果が変わり得る**。

| 日本語 | 英語の候補 | 差 |
|---|---|---|
| 和風 | `Japanese traditional` / `Japanese style` | 前者は雅楽・民謡・和楽器中心、後者は「日本っぽさ」全般 |
| 明るい | `bright` / `uplifting` / `cheerful` | 音色の話か、気分の話か |
| 壮大 | `epic` / `grand` / `majestic` | 規模か、格式か |

ラベルだけを渡してチャットAIに訳させると、この選択がAI側に委ねられる。
**ユーザーが意図を選べるようにするため、ラベルと渡す値を分離する。**

### 2-2. 曖昧な語だけに付ける

`term` を全項目に付けると、**ツール側が「英語表現の正解」を保持する**ことになり、
Suno 側の語彙が変わったときの追随コストが積み上がる。

- 訳し方で結果が変わり得る語にのみ付ける
- 一意に訳せる語（「オーケストラ」→ orchestral）には付けない
- カスタム入力には無い。従来どおりチャットAIが訳す

### 2-3. 言語別の辞書にする

```json
"term": { "en": "Japanese traditional", "ja": "和風音頭" }
```

H-03（日本語の日本固有ジャンル名が英語と同等以上に効くか）が未解決のため、
仮説が支持されたら `ja` を足せる形にしておく。

出力言語が「すべて日本語」のときは `term.en` を使わない。

### 2-4. 曖昧な語はラベル自体も区別する

`term` を分けるだけでなく、**ユーザーが見るラベルでも区別できるようにする**。

```json
{ "id": "bright-timbre", "label": "明るい（音色）", "term": { "en": "bright" } }
{ "id": "cheerful",      "label": "明るい（気分）", "term": { "en": "cheerful" } }
```

ラベルが同じだと、UI 上で選び分けられない。

上の例は説明用で、語彙ではない。当初の例「和風（伝統音楽）/ 和風（現代的）」は、伝統・現代を独立した項目「様式の寄せ方」（`input-items.md` グループ2）に分けたため差し替えた（判断ポイント117）。

### 2-5. ラベルの言語は項目ごとに決める

ジャンルには**日本語訳が定着していない語が大半**であり（Neurofunk、Vaporwave など）、
無理に訳すと逆に分かりにくくなる。

| 項目 | ラベルの言語 | 例 |
|---|---|---|
| ジャンル、副ジャンル | **一般に通用する表記**（統一しない） | `Synthwave` `City Pop` `歌謡曲` `雅楽` |
| 楽器 | 日本語を基本とし、定着語は原語 | `尺八` `エレキギター` |
| 情緒、強度、明暗など | 日本語 | `緊迫` `荘厳` |

ジャンルはラベルと `term.en` が一致することが多くなるため、`term` の出番は少ない。
逆に情緒はラベルが日本語なので `term` が効く（「明るい」→ bright / uplifting / cheerful）。

ジャンルでの運用基準は `vocabulary/README.md` の V-06。

### 2-6. 日本語が正式表記の語（`jpNative`）

V-06 で日本語ラベルになる語（`歌謡曲` `渋谷系` など）に `jpNative: true` を付ける（判断ポイント20）。
出力言語（R-08）ごとに、依頼文に渡す表記を次のとおり決める。

| 出力言語 | 渡す表記 |
|---|---|
| 標準（混在） | ラベル（日本語のまま） |
| すべて日本語 | ラベル |
| すべて英語 | `term.en`。なければラベルを渡し、チャットAI が訳す |

必要な理由: R-08 の「標準」は日本固有のジャンル名を日本語で残す定義であり、
P-01（表記をそのまま使わせる）と組み合わせると、`term.en` を持つ語でどちらの表記を使うかが決まらない。

ラベルの文字種から判定する案は採らない。判定規則がデータに現れず、
表記規則を変えたときに気づかないまま壊れるため。明示的なフラグのほうが保守的。

`jpNative` の判定基準は V-06 と同一（日本発祥で、漢字を含む通称が正式な語）。

## 3. 階層の表示

### 3-1. 代表子ノード方式

カテゴリを親、項目を子として描画する。**選択できるのは葉（項目）だけ。**
カテゴリ自体は選択できない。

```
▼ ポップス系
    ポップス
    J-POP
    K-POP
▼ 和楽器系
    尺八
    篠笛
    和太鼓
```

カテゴリ全体を指す値が必要な場合は、**その値を項目として定義し、子に置く**
（「ポップス系」の下の「ポップス」）。

注: 本ドキュメントの図や例に出てくる項目名（「ポップス」など）は説明用。
実際のラベルは `vocabulary/genres/` の語彙に従う（例: 「ポップス」は `Pop`）。
カテゴリ名も同様で、実際の一覧は `vocabulary/README.md` のカテゴリの骨格に従う
（例: §3-2 の「東アジア系」は「日本・東アジア系」）。

### 3-2. カテゴリのラベルは「〜系」とする

「ポップス」の下に「ポップス」があると読みにくいが、
**「ポップス系」の下に「ポップス」が属している**と読めば自然になる。

命名規則として固定する。`ポップス系` `和楽器系` `打楽器系` `東アジア系`。

### 3-3. 得られる不変条件

**カテゴリは決して値にならない。** これにより次が成り立つ。

| | 効果 |
|---|---|
| `selectable` フラグが不要 | 選択可否がノードの種別だけで決まる |
| 親子間の矛盾が発生しない | 「親=使用しない、子=使用する」という状態が作れない |
| カテゴリの `term` が不要 | 依頼文に渡るのは常に項目 |
| カテゴリ構成の変更が保存データに影響しない | §1-2 と合わせて |

「ポップスだが K-POP は除く」は、**兄弟の葉2つ**で表現できる
（`ポップス` = 使用する、`K-POP` = 使用しない）。表現力は落ちない。

### 3-4. 子が1つ、または代表しかない場合

**実質的な子を持たないカテゴリは、階層にせずフラットに表示する。**

```
▼ ポップス系
    ポップス
    J-POP
    K-POP
  クラシック          ← カテゴリに項目が1つしかないので直接表示
```

これは描画規則であり、データ構造は変えない。
後からプリセットに「交響曲」「室内楽」を足せば、**データを触らずに自動で階層になる**。
「その他」のような不自然なカテゴリを作る必要はない。

展開アイコンのある行とない行が混在するが、ファイラと同じなので違和感はない。

## 4. 選択UI

### 4-1. Vue + Nuxt UI を採用する（Nuxt は使わない）

**2026-09-19 に PrimeVue から Nuxt UI へ変更した**（利用者の判断）。PrimeVue が新メジャー版から PrimeUI ライセンス（オープンソースではない）に移るため、ライブラリを見直した。
候補（Element Plus、Vuetify、Nuxt UI）を同じ実データで試作して比べ、どれも §4-2 の要件を満たすことを確認した。経緯と結果は `../discussions/2026-09/11_ui-library-review.md`。

- フレームワークは Vue + Vite のまま。Nuxt フレームワークは使わない（Nuxt UI は Vite プラグインで単体で動く）
- Nuxt UI は MIT ライセンス
- 前提は Tailwind CSS 4。公式の導入例に沿う場合は vue-router も使う（必須かどうかは実装時に確認する）
- 他の資料に出る「TreeTable」は PrimeVue のコンポーネント名で、本書では「階層テーブル」（Nuxt UI の `UTable` の tree data）と読み替える

`ui-and-nonfunctional.md` §6（GitHub Pages + ローカル IIS）とは両立する（静的にビルドできることを試作で確認した。サブパスで配信する場合のルーターの設定は、実装時に確認する）。

**VueUse（Nuxt UI の依存先）も明示的な依存関係として使う**（2026-09-23）。素の Web API だけでは自前実装が必要な機能を、リアクティブな小さなラッパーで置き換える目的。現時点で使用を決めた composable は、`useColorMode`（判断ポイント32）、`useClipboard`（判断ポイント33）、`useFileDialog`（判断ポイント34）。いずれも `ui-and-nonfunctional.md` §7 に記録（`discussions/2026-09/17_ui-spec.md`）。

### 4-2. 階層のある項目は階層テーブル（Nuxt UI の `UTable` の tree data）

対象: 副ジャンル、主ジャンル、地域・文化の様式、主旋律/伴奏/リズムの楽器、基調となる情緒

| 要件 | 階層テーブルの対応 |
|---|---|
| ポップアップのネストを避ける | 展開はインライン（`get-sub-rows`）。オーバーレイを重ねない |
| 3値選択 | **セルを追加できる。** 3値の部品（ボタン群）をセルのスロットに置く |
| 検索 | グローバルフィルタ（`global-filter`）。`global-filter-options` に `filterFromLeafRows: true` を渡すと階層が保たれる |
| 高さ制御 | 表のコンテナに高さを指定し、固定ヘッダー（`sticky`）にする |
| 1列目のクリックで開閉 | セルのスロットで、行の開閉（`row.toggleExpanded()`）を結線する |
| キーボード操作 | **必須としない**（2026-09-19 利用者の判断）。旧要件は「上下で行移動、左右で開閉、`aria-level`」 |

検索は `label` に加えて `aliases`（検索用の別名）も対象にする（判断ポイント21）。
英語ラベルの語をカタカナで探せるようにするため（例: `City Pop` を「シティポップ」で見つける）。
**「検索用」の非表示の列を設けて解決する**（利用者の提案。試作で確認済み）。この列に、正規化した名前・別名・英語表記・所属カテゴリ名を入れ、
検索語も同じ規則で正規化して渡す（全角半角・大小文字・ひらがな/カタカナを区別しない）。非表示の列もグローバルフィルタの対象になる。
語の行にカテゴリ名も入れるので、カテゴリ名で検索すると配下がすべて残る。
`aliases` は依頼文には使わない。

検索中は、残ったカテゴリをすべて開き、検索を消したら検索前の開閉状態に戻す。
「非表示の語も表示」を切り替えても、開閉の状態は保つ。

階層テーブルに載るのは、表示中の語と、非表示でも状態が「未指定」以外の語である（§11-3）。

### 4-3. 選択は行選択を使わず、自前の列で行う

行選択（チェックボックス）は選択済みかどうかの2値で、
**「使用しない」を表現できない**。

したがって階層テーブルは「選択コンポーネント」ではなく
**階層表示の器**として使い、選択状態は自前の state で持つ。

3値は1列のボタン群にまとめる（列を分けると横幅を食う）。

### 4-4. ノードの key

同じ項目が複数のカテゴリに現れるため、ノードの `key` は
`打楽器系/taiko` のようにパスを含めて一意にする。
**選択状態は `id` で引く**ので、どちらを操作しても同じ状態が変わる。

### 4-5. 少数の択一項目には階層テーブルを使わない

| 項目の性質 | コンポーネント |
|---|---|
| 階層あり・多数 | 階層テーブル |
| 階層なし・少数（強度、明暗、編成規模、テンポ感、展開の形など） | ボタン群（SelectButton 相当）／ Select。Nuxt UI では `UFieldGroup` ＋ `UButton`（試作で確認）、`USelect` など |

`ui-and-nonfunctional.md` §2 の「6カードすべてで方式を統一する」とはずれるが、
あの原則の趣旨は「カード間で操作の予測が立つこと」であり、
**選択肢の性質による使い分けは許容範囲**と判断する。

### 4-6. カスタム入力

階層テーブルの外、一覧の下に常設の入力欄を置く。
追加分は「カスタム」カテゴリの下に表示し、ユーザープロファイル（旧・設定プロファイル）に保存する。
`term` は持たない。
辞典の語のうち表示を切り替えられない語（§11-3）は、この入力欄にテキストとして転記できる。

**2026-10-19 に改めた（`ui-and-nonfunctional.md` 判断ポイント49。U4）**: カスタム入力は、**項目の自由記述（`freeText`）として実装する**。楽曲データには、語彙の id と `freeText` 以外の置き場所がないため。上の記述のうち、「「カスタム」カテゴリの下に表示」「ユーザープロファイルに保存」は採らない（「カスタム」の行は作らない。保存は、プロファイルの `data` の中の `freeText`）。階層テーブルの下の常設の入力欄は残す。辞典の転記も、この欄への追記（自由記述の末尾に「, 」区切り。同じ語があれば足さない）。3値選択の項目では、自由記述は「使用する」側の追加として扱う（除外したいものは「使用しない」の語か、「除外したい要素」へ。入力欄にその旨の一言を添える）。`term` を持たない点は、従来どおり。

```
[検索: ________]

名前                    指定
─────────────────────────────────
▼ 和楽器系
    尺八                [使用する|使用しない|—]
    篠笛                [使用する|使用しない|—]
    和太鼓              [使用する|使用しない|—]
▶ 打楽器系
▶ 弦楽器系
▼ カスタム
    （ユーザー追加分）

[一覧にないものを追加: ________] [追加]

使用する: 尺八, 篠笛, 和太鼓 / 使用しない: エレキギター
```

## 5. 複数選択したときの意味

### 5-1. 列挙順に優劣はない

同一項目内で複数の要素が挙がったとき（例: 副ジャンルに `J-POP` と `K-POP`）、
**並び順は優劣を表さない**ものとする。優先したいものがある場合は
「その他・補足」に書く。

順序に意味を持たせる案は採らない。3値選択のUIに順序を入れると、
階層テーブルの表示順（カテゴリ順）と選択順が食い違い、
**並べ替え用のUIが別途必要**になる。項目数に対してコストが見合わない。

**ただし H-10 の検証待ち。** Suno 側で「先に書いたほうが優勢」と確認された場合、
この判断は見直す。

### 5-2. 冗長な指定は自動で削らない

`ポップス` と `J-POP` の両方が「使用する」の場合、両方そのまま渡す。
勝手に落とすと「指定したのに依頼文に出てこない」ことになり、
RP-02 と追跡可能性の趣旨に反する。両者は矛盾しないので害も小さい。

### 5-3. 警告の対象

`ui-and-nonfunctional.md` §5 の警告に加える。いずれも**生成は止めない**。

| 状況 | 例 |
|---|---|
| 同一項目内で近い系統を複数「使用する」 | 副ジャンルに `J-POP` と `K-POP` |
| カテゴリの代表と、その兄弟を相反する状態にした | `ポップス` = 使用しない、`K-POP` = 使用する |

後者を検出するため、代表項目に `represents` を持たせる。

```json
{ "id": "pop", "label": "Pop", "categories": ["pop-family"], "represents": "pop-family" }
```

前者（近い系統の複数使用）は、**同一カテゴリ内というだけでは判定しない**（判断ポイント22）。
Dance-pop と Synth-pop のように普通に併用する組み合わせまで警告されるため。
警告するペアを明示したリストで持ち、語彙の完成後に作成する。
表示設定によって警告の有無が変わらないよう、非表示の語もペアの対象にする（§11-3）。

## 6. 判断ポイント（既定値で進行中）

番号は `vocabulary/README.md` と**通し番号**。語彙に関する判断ポイントは同ファイルに記載する。
他のドキュメントが番号で参照しているため、分割時に振り直していない。

表記を選んだ時点で語彙はユーザーの指定になるが、要素を足す自由は残す。

## 9. 暗黙の前提

- プリセットの語彙は**ツール側が保持する静的データ**であり、ユーザーは編集しない
  （カスタム入力で追加はできるが、それはユーザープロファイル側に保存される。
  語ごとの表示の切り替え（§11）は UI 設定であり、語彙データの編集ではない）

- キーボード操作は必須としない（2026-09-19 利用者の判断）。行選択を使わないため、
  3値の切り替えは自前の列コントロール（ボタン群）の挙動になる。
  行移動・開閉のキーボード操作は、Table の組み込み機能としては確認していない（必要になったら実装で補う）

## 11. 表示の切り替えと辞典（R-19）

- 追加日: 2026-09-17（判断ポイント56〜61）
- 状態: データ形式と表示の規則は暫定。画面（§11-5）は入口・表示形式のみ決定

### 11-1. 位置づけ

語彙の選定（`vocabulary/`）で「追加しない」「除外」と判定した語も、`id` を付けて語彙データに残す。
語ごとに**既定で表示するか**を持ち、利用者は語ごとに表示を切り替えられる。
一覧に出ていない語を調べ、表示を切り替える画面を**辞典**と呼ぶ。

選定の結果は「採用 / 除外」ではなく「既定で表示 / 既定で非表示」になる。

| # | 効果 |
|---|---|
| 1 | 語彙の選定の誤りが致命的でなくなる。利用者が表示に戻せる |
| 2 | 段階4b（数による刈り込み）が削除ではなく「既定で非表示にする」処理になる（V-04） |
| 3 | 別環境で表示設定が違っても、保存データの `choices` の `id` は必ず解決できる（§1-2） |
| 4 | 楽器・情緒などの語彙にも同じ仕組みを使える。ジャンル固有の仕組みにしない |

由来: 除外した語を直接使いたい場合に参照できる「ジャンル辞典」の提案（利用者、`../discussions/2026-09/07_vocabulary-electronic-and-dictionary.md`）。
検討の途中で、既定で表示する語も含めて表示を選べる形に一般化した。

### 11-2. データ

```json
{ "id": "melodic-techno", "label": "Melodic Techno", "categories": ["electronic-family"], "aliases": ["メロディックテクノ"] }
{ "id": "trip-hop", "label": "Trip Hop", "categories": ["electronic-family"], "aliases": ["トリップホップ"],
  "defaultVisible": false,
  "exclusion": { "kind": "substitutable", "substitute": "主ジャンル Hip-hop ＋ 情緒（暗い）・テンポ感・空間の質感・音質" } }
```

| フィールド | 必須 | 内容 |
|---|---|---|
| `defaultVisible` | — | 省略時は `true`。既存の語の定義は変更不要 |
| `exclusion.kind` | ○ | 下表 |
| `exclusion.note` | kind による | 辞典に表示する説明（1文）。`substitutable`・`contained`・`count` 以外では必須 |
| `exclusion.substitute` | kind による | 代替の組み合わせ（テキスト。判断ポイント61）。`substitutable`・`contained` では必須 |
| `exclusion.targetAxis` | kind による | 行き先の軸。`other-axis` では必須。行き先がない場合は `null` |

| kind | 由来 | 表示の切り替え | 辞典での注記 |
|---|---|---|---|
| `substitutable` | V-03 (ii) / V-15。併記・同義の語も含む | 可 | 代替の組み合わせ |
| `not-instrumental` | V-03 (i) | 可 | インストでは成立しにくい |
| `vocal` | R-b | 可 | 歌唱で区別される語。インストでは差が出ない可能性がある |
| `contained` | R-c | 可 | 包含する語 |
| `count` | 段階4b | 可 | — |
| `other-axis` | R-a | **不可** | ジャンルではない。行き先の軸 |
| `hold` | 保留 | **不可** | 保留の理由 |

`categories` には、その語を審査したカテゴリを入れる。
段階3 の語の多くは V-02 の多重所属を個別に計算していないため。記録の規則は `vocabulary/README.md` の V-16。

### 11-3. 表示の規則

| # | 状況 | 扱い | 理由 |
|---|---|---|---|
| 1 | 表示設定の保存先 | UI 設定（`ui-and-nonfunctional.md` §4）。楽曲ファイル・ユーザープロファイルには含めない | 表示の有無は画面の好みで、楽曲の内容ではない |
| 2 | 表示設定の持ち方 | `id` ごとに、既定値から変えたものだけを持つ（語彙ごとに入れ子で持つ。判断ポイント205。例: `{ "genre": { "trip-hop": true, "edm": false } }`。`../specifications/presets.md` §6-2） | 語彙の更新で `defaultVisible` が変わっても、利用者が明示的に変えた語は維持され、それ以外は新しい既定値に従う |
| 3 | 切り替えできる語 | 既定で表示の語も非表示にできる。`other-axis`・`hold` の語は切り替え不可 | 軸が違う語をジャンルの一覧に出すと、軸の分離（画像版 P5-01 の教訓）が崩れる |
| 4 | 非表示の語が指定済み | 状態が「未指定」以外なら一覧に出す（非表示の印付き） | 指定中の語が見えなくなると、RP-02 の「状態を常に見えるようにする」趣旨に反する |
| 5 | 警告（§5-3） | 表示設定に関係なく判定する | 表示設定で警告の有無が変わらないようにする |
| 6 | 依頼文 | 表示設定の影響を受けない。指定された語は表示中の語と同じ規則（§7）で渡す | 表示は UI の問題で、指定の意味を変えない |
| 7 | `other-axis`・`hold` の語を使いたい場合 | カスタム入力（§4-6）にテキストとして転記する。`id` 参照にはしない | カスタム入力は自由記述なので使うことは妨げない。`id` を参照させるとプリセットのジャンルとして扱われる |
| 8 | 辞典の収録範囲 | 語ごとの判定記録がある語のみ（V-16） | 記録のない語は理由も代替も示せない。それらはカスタム入力で使う |
| 9 | V-13 の語数 | 既定で表示される語だけを数える | 利用者が表示を増やした結果は利用者の選択 |

### 11-4. カテゴリの別名

カテゴリに検索用の `aliases` を持たせる。

```json
{ "id": "electronic-family", "label": "エレクトロニック系", "order": 40, "aliases": ["ダンス", "Dance", "ベースミュージック", "Bass Music"] }
```

これは「この分類を探す手がかり」であり、項目の `aliases` と違って同義性を求めない（判断ポイント21 の対象外）。
依頼文には使わない。別名にする名称の決め方は `vocabulary/README.md` の V-14 (6)。

階層テーブルでは、語の行の「検索用」の列にカテゴリ名も入れるので、カテゴリ名で検索すると配下がすべて残る（試作で確認済み）。
カテゴリの `aliases` も、同じ列に入れる（項目の `aliases` と同じ規則。試作ではカテゴリ名と別名を入れている）。
