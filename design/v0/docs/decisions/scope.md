# スコープ・方針（R-xx / L-01）

- 最終更新: 2026-10-18（L-01b: 初版は新規生成のみに改訂。派生生成は第2段階）。〔経緯〕2026-09-17

---

## 0. ツールの目的

チャット系AI（ChatGPT / Claude / Gemini など）に対して、
**音楽生成AI用プロンプトの作成を依頼するための依頼文**を組み立てるツール。

- 音楽生成AI の API は直接呼ばない（画像版と同じ）
- 出力はクリップボードへのコピーで完結する
- チャットAI の回答を取り込む・解析する機能はスコープ外
- 利用者は本人のみ

位置づけ: Suno 自体にもスタイル補助機能（スタイル欄の魔法の杖アイコン）がある。
本ツールの価値は「スタイルの文章を作ること」そのものではなく、
**要件を構造化し、判断のぶれなくチャットAI に伝えること**にある。画像版と同じ位置づけ。

## 1. R-01: 対象の音楽生成AI【確定】

**Suno を主対象とする。**

- 将来、他サービスやローカル実行型（Stable Audio 3 等）を利用する可能性は否定しない
- ただし初版で実装するのは Suno プロファイルのみ
- 「汎用（ツール非依存）」プロファイルは初版では実装せず、構造上追加できる状態にとどめる

この決定により、ツール固有情報のデータ分離（R-10）は「提案」から**設計要件**に格上げされた。

## 2. R-02: 歌詞の扱い【一部確定】

| 区分 | 扱い |
|---|---|
| インスト中心（歌詞不要） | **対象** |
| AI に作詞まで任せたい | **対象**。ただし「どの AI が作詞するか」の観点で別議論が必要（L-01） |
| 自作歌詞を渡して整形 | **スコープ外**（将来追加可能な構造にはする） |

### 初版（MVP）の範囲

**初版はインストのみを実装する。**

- 理由: L-01 が未決着のため、初版の仕様を作詞議論の待ちで止めないため
- ただし後からのマイグレーションを避けるため、以下の軸は**データ構造に初版から確保**する
  - ボーカル区分（インスト / ボーカルあり）
  - 段階の識別（新規生成 / 派生生成）と、派生生成の操作種別
  - 作詞の主体（L-01a の値。初版では未使用）

初版のインスト生成は「インスト先行 → 派生で歌付け」フローの第1段階そのものにあたるため、
初版は行き止まりにならない。

## 5. R-05: 保存【暫定】

初版から JSON エクスポート / インポート + `schemaVersion` を持つ。

- 画像版は保存機能を後回しにした結果、Phase 5 で schemaVersion とマイグレーションが必要になった
- 保存 UI 自体は後回しでもよいが、**FormData は初版から JSON 化可能な形で設計する**
- 派生生成では第1段階の入力内容を引き継ぐ必要があるため、保存の重要性はさらに高い

保存は3種類（自動保存 / ユーザープロファイル / ファイル入出力）に、画面の見え方の設定（UI 設定）を加えた4つに分ける。
詳細は `ui-and-nonfunctional.md` §4、データの形は `../specifications/song-file.md` を参照（2026-09-21）。

なお「プロファイル」は R-10 の「ツールプロファイル」と語が衝突するため、
**ユーザープロファイル**（利用者が保存する入力内容。旧・設定プロファイル）と
**ツールプロファイル**（Suno などの仕様定義）で呼び分ける。
アプリに同梱する入力の見本は**ファクトリープロファイル**（保存の種類には数えない）。

## 6. R-06: 技術スタック【暫定】

Vite + **Vue** + TypeScript。UI コンポーネントは **Nuxt UI**（Nuxt フレームワークは使わない）。

- **2026-09-19 に PrimeVue から Nuxt UI へ変更した**（利用者の判断）。PrimeVue が新メジャー版から PrimeUI ライセンス（オープンソースではない）に移るため。
  経緯と候補の比較、試作の結果は `../discussions/2026-09/11_ui-library-review.md`
- 画像版は React だったが、音楽版では**階層テーブル**（Nuxt UI の `UTable` の tree data）を使うため Vue にする
  （ジャンルや楽器の階層選択を、ポップアップをネストせずに実現するため。`presets.md` §4。当初は PrimeVue の TreeTable が理由だった）
- Nuxt UI の前提は Tailwind CSS 4（公式の導入例に沿う場合は vue-router も使う）。MIT ライセンス
- R-07 で画像版とコードを共通化しないと決めているため、フレームワークが違っても支障はない
- 画像版は Artifact で開始して長大化により移行した経緯があるため、
  **最初からローカル環境で開発する**

## 8. R-08: 生成物の言語【暫定】

- 依頼文とチャットAI の説明: 日本語（固定）
- スタイル欄・除外欄の言語: **ユーザーが選択する**

### 選択肢

| 選択肢 | 内容 | 想定する用途 |
|---|---|---|
| すべて英語 | 日本固有の語も英訳する（`Japanese festival ondo`） | Suno の認識精度を重視する |
| すべて日本語 | 全体を日本語で書く | 日本語の語感で作りたい。日本固有のジャンルが中心 |
| **標準（混在）← 既定** | 英語を基本に、日本固有のジャンル名・様式名は日本語 | 実例に最も近い |

既定を「標準（混在）」としたのは、実例（`Japanese Traditional, 和風音頭, 演歌`）で
実績がある選択肢を選んだ保守的な判断。

### 優劣を示さない

3つのうちどれが最も良い結果になるかは、現時点で判断材料がない。
第三者情報は「英語のほうが認識精度が高い」とするが、対象バージョンは v4.5〜v5 期。

→ **選択肢を提供するが、優劣は示さない。**
UI の説明文には「Suno は日本語も解釈できる」という事実だけを書き、推奨は付けない。
H-03（日本語ジャンル名の効き方）の検証結果が出たら見直す。

### 根拠

- 第三者情報では「英語のほうが認識精度が高い」とされる（対象バージョン v4.5〜v5 期）
- 実例では日本語タグ（`和風音頭`, `演歌`）が使われ、Suno 側の自動キャプションにも
  「演歌風」として反映された（ただし英語の `Japanese Traditional` の効果と切り分けられていない）
- 実例の生成曲2 では **Suno 自身が日本語のみでスタイルを書き換えた**。
  Suno が日本語で完結したスタイルを生成する以上、日本語のみの入力も機能すると考えるのが自然
- 歌詞生成用のプロンプトも日本語解釈可能

### 注意

- バリエーションが「オフ」以外の場合、**最終的なスタイルの言語は制御できない**
  （同一入力でもテイクにより英語 / 日本語が入れ替わる）。
  この選択が実質的に意味を持つのは「オフ」の場合
- 歌詞の場合は「指示文の言語」と「歌詞本文の言語」が**別の軸**になる（L-01 で扱う）
- 日本語は英語より1文字あたりの情報量が多い（実例: 英語中心約200文字 / 日本語中心約90文字）。
  上限 1,000文字に対してはどちらも余裕があるため、
  推奨長の言語別管理は**実害が出るまで保留**する。
  言語の密度に関する調整は運用しながら行う

## 10. R-10: ツールプロファイル【暫定】

ツール固有情報を依頼文生成ロジックから切り離し、データとして保持する。

### 保持する情報

- **出力フィールドの定義**: フィールド名、文字数上限、推奨長、記述言語、指定経路
- **機能の有無**: 除外欄、メタタグ、インスト切替 → 依頼文のルールブロックを出し分ける
- **固有パラメータ**: 名前、値の範囲、既定値
- **禁止・注意事項**: アーティスト名の扱い、上限超過時の挙動
- **モード ＞ 操作種別の2階層**: Suno のリミックスモードには操作が15種類あり、
  操作ごとに使える項目が異なる
- **必要プラン**: 操作ごと（なし / Pro / Premier）
- **アカウントに紐づく要素**: 作詞家、Voice、Custom Model、パーソナライズ
- **情報のメタデータ**: 確認日、情報源、**対象バージョン**

### 上限値の3状態

| 状態 | 意味 | 例 |
|---|---|---|
| 確認済み | 値がわかっている | スタイル 1,000文字 |
| 下限のみ判明 | 少なくともこれ以上入る | （現時点で該当なし） |
| 不明 | 値がわからない | 作詞AI への指示 |

### 上限と推奨長を分ける

入力できる上限と、良い結果を得るための長さは別物。両方を保持する。

- 曲名: 上限80文字だが、推奨長はさらに短く
- 歌詞: 上限5,000文字だが、長すぎると品質が落ちる可能性。
  推奨長は**言語ごとに持つ必要がある**（日本語と英語で1文字あたりの情報量が異なる）
- 作詞AI への指示: 上限不明のため、推奨長のみで運用

### 段階概念とモードの対応

- **段階**（新規生成 / 派生生成）: 本ツール側の、ツール非依存の概念
- **モード**（通常 / リミックス）: Suno 固有の概念
- 両者の対応はプロファイルが持つ。段階の概念がないツールでは対応を持たなければよい

### データ仕様（2026-09-21）

形は `../specifications/tool-profile.md`（判断ポイント1〜8）に定めた。上の記述との対応は次のとおり。

- 「モード」は、通常／リミックスのまま。Suno の画面切り替え（シンプル／アドバンスド／サウンド）は「画面」として別に持つ
- 上限値の3状態は `limit.status`（`confirmed`／`lowerBound`／`unknown`）
- 必要プランの「—」は、「なし」と読まず `null`（不明）とする
- 操作は15種すべてを記録し、依頼文の対象にするかを `scope` で表す（テキスト指示を伴わない操作は対象外。§19）

## 12. R-12: Suno固有パラメータの扱い【暫定】

RP-02 の値の状態区分で統一的に扱う。

- ②お任せ → チャットAI に推奨値を出させる
- ③Suno既定 → 既定値のまま。依頼文には値を明記する
- ①指定 → ユーザーが決めた値を依頼文に明記する

### パラメータの分類

| 分類 | 項目 |
|---|---|
| 依頼文への入力として使う | ボーカル性別、長さ、**バリエーション** |
| 推奨値を出させる候補 | 奇抜さ、スタイルの影響、Maxモード、オーディオの影響（派生時） |
| 依頼文の対象外 | パーソナライズ（利用履歴依存でチャットAI に判断材料がない） |

### バリエーションが特別な理由

バリエーションの設定により、**チャットAI が書くスタイルの役割が変わる**。

- **オフ**: チャットAI が書いたスタイルが**そのまま最終形**になる
  → 必要な要素をすべて含む完成した記述を書かせる
- **オフ以外**: チャットAI が書いたスタイルは Suno が書き換える**元ネタ**になる
  → 細部を書き込むより、核となる要素を短く前方に置かせる

このためバリエーションのみ「ユーザーが決めて依頼文に伝える入力」として扱う。

## 13. R-13: UI設定と本文の二重指定【暫定】

ボーカル性別・長さなどは UI 設定でも指定でき、スタイル欄の本文でも表現できる。
両方で指定できる項目は矛盾や重複が起こり得る。

対策: プロファイルの各項目に**「指定経路」属性**を持たせる。

| 経路 | 意味 |
|---|---|
| 本文 | 欄のテキストで表現する |
| UI設定 | UI 設定でのみ指定する。本文には書かない |
| 併用 | UI 設定と矛盾しない範囲で本文にも書いてよい |

依頼文では RP-05 がこの属性に基づいて指示を出す。

由来: 画像版の「解像度とアスペクト比はプロンプト外の設定で指定できるため、
プロンプトに含めない」というルールの一般化。

どの項目をどの経路にするかは、入力項目の議論で項目ごとに決める。

## 14. R-14: 曲名の扱い【暫定】

- 曲名を空欄にすると Suno が自動設定する
- 観察（仮説）: 自動設定される曲名の言語はスタイルに依存する可能性がある
  （スタイルに `Chinese traditional` と指定すると中国語のタイトルになる場合があった）
- さらに仮説: 依存先は入力したスタイルではなく**書き換え後のスタイル**の可能性がある
- 確認済み（2026-09-16、H-07 の検証より。**2026-09-17 に訂正**）:
  曲名はテイクごとではなく**生成リクエスト（1回2曲）単位**で決まり、同じ入力でも生成ごとに変わり得る。
  当初は「入力スタイル単位」としていたが、H-09 の検証で同じ入力の2回の生成が別の曲名になり反証された（H-08）。
  言語の切り分けは未達成（H-02 継続。ただし、書き換えのない条件でもスタイルの内容で言語が変わる観察がある。`../examples/suno-test-02-jp-traditional-vs-style.md` §6-4）

依頼文のオプションとして次を持たせる。

- 曲名案をチャットAI に出させるか
- **出させる場合の希望数**（既定 3）
- 出させる場合の言語

### 曲名案の数を複数にする理由

**同一のプロンプトで複数の曲を作成する可能性がある**ため。

### プロンプトの案との関係

| 案 | 内容 |
|---|---|
| A | プロンプトの案ごとに曲名案を出す（3案 × 3曲名 = 9個） |
| **B ← 採用** | プロンプト全体に対して曲名案をまとめて出す（3個） |

B を採る理由: 曲名は**同じプロンプトから生まれる複数の曲に付けるもの**で、
プロンプトの案とは独立している。
回答フォーマットでは、曲名案を案ごとの出力ではなく**末尾にまとめて置く**。

ただし、プロンプトの案ごとに曲の性格が変わる場合、曲名も変わるべきという考え方もあり得る。
既定は B とし、必要なら後から選択式にできるようにしておく。

なお、派生生成では Suno が自動で `(Add Vocal)` 等を付けるため、
曲名案は不要な可能性が高い。

参考: v5.5 期の第三者情報では「曲名欄は音楽の出力にほとんど影響しない」とされるが、
v6 では未検証。「曲名は音楽内容に影響しない」とは仕様上まだ前提にしない。

## 15. R-15: 長さと構成の関係【暫定】

- 長さは **UI 設定なので確定条件**として扱える
- 本文中の構成指定は**参考情報**として扱う
  （メタタグは確率的なヒントであり、BPM も厳密には固定されない）
- 長さのカスタム指定と構成の矛盾（短く設定したのにセクション数が多い等）への対処が必要
- 操作によって長さの扱いが変わる。プロファイルで操作ごとに定義する
  - 「ボーカルを編集」: 長さは元曲で決まる → 依頼の対象外
    （実例: 元曲 3:00 → Add Vocal 版 2:58〜2:59）
  - 「延長」: 長さが意味を持つ

### 入力値の扱い

- 内部の値: 整数の秒数（10〜360）。保存形式（JSON）もこれに合わせる
- 入力欄: 秒数と M:SS 形式の両方を受け付ける（Suno と同じ）
- 表示・依頼文での表記: M:SS 形式（Suno の表示と一致させる）
- 検証: 10〜360 の整数秒。5秒単位には丸めない
  （スライダーの刻みが5秒なだけで、キーボード入力は1秒単位）

画像版 Phase 3 の入力値検証（範囲チェックと自動補正ダイアログ）と同じ仕組みで扱える。

## 17. R-17: 出力する粒度（基本プロンプト）【一部確定】

バリエーションがオフ以外だと Suno 側でスタイルが変更される。
その前提なら、**必要最低限の短めのプロンプト（基本プロンプト）**を発行させてもよい。

これにより、以下は**独立した2本の軸**として扱う。

- **粒度の軸**: 基本プロンプト / 詳細プロンプト
- **設定の軸**: 想定するバリエーションの値（R-12）

両方を出させれば、Suno 側で組み合わせを生成時に選べる。
**依頼文を出し直さずに試行錯誤できる**のが利点。

詳細な定義と副次的効果は `request-format.md` §2 を参照。

### 検証結果（H-07、2026-09-16）

「基本＋バリエーション標準」と「詳細＋オフ」を 16 項目のチェックリストで採点した結果、
**両条件とも 15.5/16 で差 0.0（同等）**だった。

規則に従い、**Suno 側の使い分けは「詳細＋バリエーションオフ」を既定**とする。
入力と出力の対応が追跡でき、同じ入力から同じ結果が得られるため。

ただし両条件とも満点近くで、**差を検出する感度がなかった**（天井効果）。
正確には「この要件セットでは差を検出できなかった」。
詳細は `../examples/suno-test-01-granularity.md` §9。

**依頼文側の既定は引き続き「両方出力」**。
両方あれば依頼文を出し直さずに組み合わせを試せるという利点は変わらない。

## 18. R-18: カバー画像との連携【未着手・初版スコープ外】

曲のテーマに合ったカバー画像を画像生成AI（SD など）で作りたい場合の扱い。

### 選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A | 本ツールにカバー画像用の依頼文生成を追加 | スコープが大きく広がる。画像側の入力項目が必要になり、ツールの目的が2つになる |
| **B ← 推奨** | **画像版ツールに渡すための「楽曲の要約」を出力** | スコープが小さい。既存の資産（画像版）を活かせる |
| C | 依頼文に「カバー画像用のプロンプトも出して」と追記 | 手軽だが、画像版の判断ぶれ対策が効かない |
| D | 対象外 | — |

B を推奨する理由: 画像版ツールには画像固有の判断ぶれ対策
（18項目、Phase 4 の成果）が組み込まれている。
音楽版で画像のプロンプトを一から作ると、その資産を捨てることになる。

### B 案の具体化

軸は完全には対応しない。

| 画像版の項目 | 音楽版から渡せる内容 |
|---|---|
| 用途 | 「楽曲のカバー画像」と固定 |
| テーマ・被写体 | 用途・文脈（軸A）、地域・文化の様式（軸B） |
| 雰囲気 | 基調となる情緒、強度、明暗（軸C） |
| 画風 | 音質・質感（軸F）から類推、または未指定 |

軸D（音の構成）と軸E（時間的な構造）には画像に対応するものがない。
逆に、画像版には構図や光といった、音楽側に対応がない項目がある。

→ 機械的な項目変換ではなく、**曲の情景を言葉にした短い要約**とする。

```
## カバー画像用の要約（画像版ツールの「その他・補足」欄などに貼る）

夏祭りの夜。赤い提灯が揺れ、太鼓の音が響く。
浴衣姿の人々が行き交う賑やかさと、夏の終わりの寂しさが同居する情景。
```

画像版の構造化された項目はユーザーが画像版側で入力し、
音楽版は**文脈の橋渡しだけ**を担う。

### 出力の制御

出力設定（グループ9）に項目を追加する。既定はオフ（毎回必要なものではないため）。

| 項目 | 型 | 既定 |
|---|---|---|
| カバー画像用の要約を出させるか | オン/オフ | オフ |

### 初版スコープ外とする理由

依頼文の文面すら未確定な段階で出力項目を増やすと、中核の検証が遅れるため。

### 暗黙の前提

画像版ツールが今後も使える状態で維持される前提。
画像版は Phase 5〜6 の大改修を控えているが、
入力欄の構造が変わっても「文章を貼る」という受け渡し方法は維持されると見ている。

## 20. L-01: 作詞（別議論）【一部確定（2026-09-28）】

当初は「誰が作詞するか」の一軸と考えていたが、少なくとも3つの独立した軸がある。
画像版 P5-01（軸の混在による後からの分離とマイグレーション）の教訓から、事前に分離しておく。

### L-01a: 作詞の主体

| パターン | 内容 |
|---|---|
| A | チャットAI が作詞する。依頼文に作詞要件（テーマ、言語、構成タグ、読み対策等）を含める |
| B1 | Suno の Simple モード（曲全体を Suno に任せる）。v6 で Simple モードの表現力が上がったため再評価が必要 |
| **B2** | **Advanced モードで、Suno 作詞AI に指示文を渡す**。チャットAI が出すのは歌詞ではなく「Suno 作詞AI への指示文」 |
| C | 作詞を別の AI や別スレッドに分ける。本ツールが「作詞依頼文」を別出力として生成 |

B2 には下位の選択肢として「作詞家（歌詞ペルソナ）を使う / 使わない」がある。

**2026-09-28 決定**: A と B2 の両対応とする（依頼ごとに選ぶ。`lyricsAuthor` が①指定必須の列挙値）。B1・C は初版では不採用。詳細は `input-items.md` 判断ポイント20。「両方生成」モードは将来の拡張候補（`both`値。今回は実装しない）。

### L-01b: 生成の手順

| パターン | 内容 |
|---|---|
| 一発生成 | 歌付きで最初から作る |
| **インスト先行 → 派生で歌付け** | 実例で成立を確認済み。第一候補 |
| v6 の言葉による編集 | 「サビをゴスペル聖歌隊が歌うように変える」等の指示で区間を変更。インスト→歌付けに使えるかは未検証 |

**2026-09-28 決定**: 「インスト先行 → 派生で歌付け」（`edit-vocals`）を初版の推奨経路とする。元曲スタイルの扱いは既存の `sourceStyleText`／`sourceStyleEditMethod` を流用し、`keep` を推奨値にする（`input-items.md` 判断ポイント22）。「一発生成」（`generationType: new` ＋ `vocalMode: vocal`）も、`lyricsAuthor` 等の新項目は共通に使えるため構造的には可能だが、未検証のまま残す。

**2026-10-18 改訂（利用者の判断。F6 の扱い）**: **初版は新規生成のみ（F6 維持）とし、`edit-vocals` 経路を含む派生生成は第2段階へ移す。** 初版の歌付けは「一発生成」（`generationType: new` ＋ `vocalMode: vocal`。`lyricsAuthor`・歌詞の3項目で提供。依頼文は `request-text.md` のレンダリング例 `-07`〜`-12` で6モデル検証済み）で行う。理由: (1) 派生生成の UI（派生元カード、複数の依頼の切替、元曲の選択）が未設計で、実装前の設計が増える。(2) データ形式は初版から確保済み（`derivedFrom`、スキーマ、F3・F9〜F11）で、第2段階では F6 を外して UI と文面を足すだけで済む。(3) 検証済みの B-DF・B-03d は資産として残る。第2段階の作業は `../handoff-next-thread.md` 宿題48。初版の推奨経路は、上の 2026-09-28 の決定から「一発生成」に変わる。

### L-01c: 発行の単位

| パターン | 内容 |
|---|---|
| 1依頼・分割出力 | 1つの依頼文で、出力をスタイル部と歌詞部に分けて返させる |
| 依頼文の分割 | 依頼文そのものをスタイル用と歌詞部用に分ける |

L-01b で「インスト先行」を選ぶと、歌詞部の依頼は後日の別作業になるため、
L-01c は自然に「依頼文の分割」側に寄る。

**2026-09-28 決定**: L-01b の推奨（インスト先行→派生で歌付け）に従い、「依頼文の分割」を採用する。

**2026-10-17 注記**: 初版の実装（`request-blocks.md` §3-3、`request-text.md` の B-LY 系）は、1つの依頼文でスタイルと歌詞（または作詞AIへの指示文）を両方出させる形で、歌詞部を独立したブロックと独立した出力の項に分けることで、この決定を満たすものとした（`request-text.md` §5 判断ポイント27）。スタイル用と歌詞用の依頼文そのものを分ける形は未実装。案件ごとに1依頼／2依頼を選べる拡張は将来の候補（利用者の所見。`edit-vocals` 経路の再整理とあわせて検討）。

### 共通の論点

- 歌詞は既存曲の模倣リスクが画像より高い（著作権ルールの強化が必要）
- 日本語歌詞の読み対策（下記）
- 構成タグと歌詞の責任分担
- 歌詞の推奨長を言語ごとに持つ必要がある
  - 日本語: 約3分の曲なら200文字以内が理想（第三者情報）
  - 英語: 3,000文字程度までが品質の目安（v5.5 期の第三者情報）
  - 両者は1文字あたりの情報量が違うため単純比較できない

### 日本語歌詞の発音対策（第三者情報）

- 読み方が複数ある漢字は、ひらがなで書くと意図どおりの発音になりやすい
- カタカナ語は英語風に発音されることがあるため、ひらがなのほうが日本語らしくなる
- 「を」「は」など発音が特殊な助詞は、その部分だけローマ字にすると調整できる。
  ただし多用すると不自然になる

パターン A では依頼文の「作詞要件」オプションとして使える。
パターン B2 では Suno 作詞AI の出力に漢字が含まれるため、
**Suno が書いた歌詞を後から直す工程**が必要になる可能性がある。

**2026-09-28 決定**: 新しい項目（トグル）にはせず、パターン A ＋日本語のときだけ依頼文に固定の注意書きを含める（`input-items.md` 判断ポイント25）。

## 21. 画像版から引き継ぐ教訓

| 画像版で起きたこと | 音楽版での対応 |

| Artifact で開始し、長大化して移行 | 最初からローカル環境で開発（R-06） |

## 22. R-19: 語の表示の切り替えと辞典【暫定】

- 追加日: 2026-09-17
- 状態: データ形式と表示の規則は暫定。画面の形は未着手。初版に画面まで含めるかは実装段階で決める

語彙の選定で除外した語も `id` 付きで語彙データに残し、語ごとに「既定で表示するか」を持たせる。
利用者は、既定で表示される語も含めて表示を切り替えられる。一覧にない語を調べる画面を「辞典」と呼ぶ。

| 要点 | 内容 |
|---|---|
| 由来 | 除外したジャンルを直接使いたい場合に参照できる「ジャンル辞典」の提案。検討で全語の表示切り替えに一般化した |
| 効果 | 語彙の選定の誤りを利用者が補える。段階4b（数による刈り込み）が削除ではなく非表示になる |
| データ形式と表示の規則 | `presets.md` §11 |
| 表示設定の保存先 | UI 設定（`ui-and-nonfunctional.md` §4-6）。楽曲ファイル・ユーザープロファイルには含めない |
| 語彙への記録 | `vocabulary/README.md` の V-16 |

データ形式だけを先に決めたのは、語ごとの判断をしている語彙の作成中が、記録の手間が最も小さいため。
