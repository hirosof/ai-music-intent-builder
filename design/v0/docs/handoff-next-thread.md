## 4. 教訓（次スレッドで踏襲すべき運用）

前スレッドまでの教訓（4-1〜4-20）は、内容を保ったまま引き継ぐ。4-21 以降が今回のスレッドの教訓。

### 4-1. 自由記述の逃げ道がない項目は特に慎重に

テンポ感・空間の質感・音質・録音の質感・ミックスの方向性の4項目は、自由記述の逃げ道がない（判断ポイント8）。実際には、選択のみの項目は他にも7つあり、11項目になる（`input-items.md` 判断ポイント15。現状のまま記録）。語彙を見直すときは、他の軸より一段厳しくカバレッジを検討する。

### 4-2. 「対称性による拡張」は一度立ち止まって線を引く

対称性だけを根拠にプリセットを増やし続けると、際限がなくなる（判断ポイント199）。「すでに追加した対称的な語は残すが、それ以降の同種の拡張は自由記述に任せて止める」。

### 4-3. Suno 実測データは最強の根拠。積極的に集める

利用者の実験データ（`examples/suno-test-*.md`）は、一般知識より遥かに説得力がある。声の扱いの `humming`・`scat` などの語や、「しない」の値の依頼文での扱いは、まだ検証していない。

### 4-4. 書き込み後の確認（更新）

日本語の書き込みで、文字が別の字に化ける事故が、複数スレッドで繰り返し起きた。

- **日本語を `\uXXXX` のエスケープで渡さない。** 「合唱」が「合唇」、簡体字「辽」の混入、「弾」が「弹」になった。日本語は直接入力する
- **書き込んだファイルは、読み戻して照合する。** `copy_file_user_to_claude` で私の環境に取り込み、`cmp` で検証済みの版と照合する。`edit_file` の差分表示も、その場の確認になる
- **文字化けは、機械でスキャンする。** `cp932` で符号化できない文字を検出すると、簡体字や別の字の混入を拾える（記号や欧文のアクセント付き文字は許容リストに入れる）。編集した文書は、書き込みの区切りごとにスキャンする
- **大きなファイルは、私の環境で検証してから書き込む。** 直接書くより、検証済みの版を渡すほうが安全
- **`edit_file` の `oldText` は、実ファイルから取った文字列を使う。** 記憶や推測で書くと、一致しない
- `copy_file_user_to_claude` は、**同名のファイルを上書きする**（`README.md` など）。連続して取り込むときは、都度、別名で退避してから使う
- 従来の `view_range` 付きの読み取りも有効
- `copy_file_user_to_claude` は、ファイル名の `.` を `_` に置き換える（`song.schema.json` → `song_schema.json`）。取り込んだ後、必要なら正しい名前で配置し直す
- 読み取りの表示に、実ファイルにない文字化け（U+FFFD）が出ることがある。疑わしいときは、取り込んで厳密な UTF-8 復号で確かめる

### 4-5. 進捗メモは後回しにしても実害は小さい

判断ポイントの表は、その場で正確に記録する。進捗の要約は、時間が厳しければ後回しにしてよい。

### 4-6. 決めていない設計を、確認せずに採らない

利用者が継続している設計や、複数の選択肢がある論点を、一方的に排除しない。事実を示し、既定案を添えて、承認を得る。既に承認された設計を変えるときは、変更する理由を先に述べる。

### 4-7. 「見つからなかった」を「できない」にしない

**「未確認」と書く。** 公式のサンプルが機能ごとに別々に載っているだけのことがある。

### 4-8. 検証できるものは、スクリプトにして、負例で確かめる

**手で数える・目で見るより、生成・検証する。** 行数やサイズも、実測して報告する。

### 4-9. jsdom のテストは構造だけ。見た目は目視

**不具合は、まずテストで再現してから直す。** 目視が必要な範囲は、前もって明示する。

### 4-10. 識別子は、言語の予約語を避ける

実際に試して、値やキーとしては問題ないことを確かめたうえで、混乱の余地をなくす名前にする。

### 4-11. 1ターンの作業量を意識する

大きな作業では、ツールの使用制限に達することがある。利用者の環境では、「続ける」ボタンが「続ける」というメッセージとして投稿される。**作業は、1ターンで完結する単位に分け、区切りごとに要約を出す。** 途中で切れた場合に備えて、成果物を都度、書き込んで確認する。

### 4-12. 決めることは「要判断」「既定案」「補完」に分けて出す

**結果が大きく分岐する点だけを、選択肢と推奨つきで求め、他は既定案として併記する。** 承認の内側で補った項目（値の名前、`id` の形式など）は、補完・仮定一覧に済ませる。

### 4-13. 一度で全部通ったテストは、検査を壊して確かめる（変異テスト）

検査側を意図的に壊して、テストが検出するかを確かめる。`jsonschema` の有無など、環境を変えた実行（模擬）も併せて行う。

### 4-14. 実データのない環境での検証は、その旨を明記し、実環境での実行を依頼する

報告するときに、最小の語彙・写しでの結果であることと、実環境で実行してほしいコマンド・想定結果を示す。

### 4-15. 検証の実行環境の癖

`bash_tool` のシェルは `sh` で、`${PIPESTATUS[0]}` などの配列変数は `bash -c '...'` で実行する。出力の切り詰め（`cut -c`）は日本語をバイトの途中で切り、出力が無効な UTF-8 になる。Python で切る。1コマンドの実行時間は300秒まで（教訓4-25）。

### 4-16. 用語を変えるとき、過去の記録は残す

現在の記述は新語に直し、変更前の決定の記録は旧称のまま残して、新しい行に注記する。旧称は、他の文書に残っている可能性がある（未掃引。触るときに直す）。

### 4-17. 検査を壊す確認は、「降格」だけでなく「出力を消す」で行う

エラーを注に降格する壊し方では、メッセージ本文が残り、同じケースに別のエラーも出るため、終了コードが変わらず、テストが通ったように見える。**出力そのものを消す壊し方に改めて判定し直す。** 壊し方は2通り以上で確認する。

### 4-18. 新しい引数・変数は、既存の全形式の例で実行して、名前の衝突を確かめる

**正例が複数の形にあるなら、すべてを実行してから書き込む。**

### 4-19. 仕様書が予告する「反映先」は、実物で確認してから書く

記録の主張は、grep などで実物に当たってから書く。

### 4-20. `edit_file` は複数の差分を1回で適用できる。適用後は取り込んで照合する

私の環境で差分を作って検証し、同じ差分を `edit_file` の `edits` 配列で適用し、取り込んで `cmp` で照合する。バイト照合ができないファイル（文書）は、差分の目視と `cp932` の走査で確認する。

### 4-21. 例外を捕まえて報告するチェッカーでは、「落ちなかった」の確認に `Traceback` は使えない

エラー・警告の件数と、変換後のメッセージ（例:「F0 構造が不正」）がないことを確かめる。変異テスト（教訓4-13・4-17）で見つかった。

### 4-22. 日本語の `\uXXXX` 渡しは、意識しても再発する

教訓4-4で禁止を明文化した後も、複数のスレッドで繰り返し発生した（このスレッドだけで7回以上）。**「気をつける」は対策にならない。** 差分の目視に加え、書き込み後は必ず「取り込んで元の版・意図した文字列とバイト照合または機械的な差分を取る」手順を、例外なく踏む。

### 4-23. `copy_file_user_to_claude` の取り込み先は読み取り専用

`mv` はできず `cp` は使える。同名のファイル（例: `input-items.md` が `decisions/` と `specifications/` の2か所にある）は、取り込みのたびに上書きされるので、その都度 `cp` で別名に退避してから、次のファイルを取り込む。

### 4-24. 複数ファイルの一括読み取りの結果には、ファイルの区切り（ファイルパスの行、空行）が混ざる

元の版として差分に使うときは、区切り行を取り除いてから比較する。

### 4-25. 1コマンドの実行時間は300秒まで

変異テスト（1種あたり数秒〜数十秒）は、まとめて1コマンドで流すと制限に達することがある。種類を分けて実行する。

### 4-26. `edit_file` の複数編集は原子的。1件でも不一致なら全体が無変更に戻る

これは安全に働く（部分適用による中途半端な状態を防ぐ）が、**大きな一括編集の前には、対象ファイルを直前に取り込んだ内容に対して、Python で全 `oldText` の出現回数（=1）を検証してから提出する。** 失敗した場合は、ファイルが無変更であることも確認できる（教訓4-4の「照合」の一部として）。

### 4-27. 日本語の手打ちでの誤字・かなの混入・全角数字化は、意識しても頻発する

教訓4-4・4-22の対策（照合）を徹底していても、**入力の時点**での誤字（例: 「挿入」を「挙入」と誤変換、存在しない「よ」の混入、半角数字が全角「２３」になる）は防げなかった。書き込み前の照合だけでは、そもそも編集が失敗して何も書き込まれない（教訓4-26）ため実害は小さいが、やり直しの手間になる。**対策: 数字や、視覚的に紛らわしい漢字（挿／挙など）を含む `oldText`／`newText` は、Python で生成した文字列をそのまま使う（手で再入力しない）か、当該の数字・漢字を含まない最小限の断片に分割して、複数の小さな置換に分ける。**

### 4-28. `edit_file` のエラーメッセージでの全角・半角の表示は、実ファイルと一致しないことがある

`oldText` 不一致のエラーで返される「現在の内容」の数字の全角／半角が、直前の `read_text_file` の結果と異なって見えることがあった（実際のファイルは後者が正しかった）。**エラーの文話を直前の読み取りの書き写しとして信頼せず、失敗したら即座に `read_text_file` で対象範囲をもう一度取り直し、そこから得た文字列を `oldText` に使う。**

### 4-29. 選択肢 UI ツール（`ask_user_input_v0` 等）のテキストも、日本語の区切り記号が破損することがある

ファイル書き込みだけでなく、チャット上の選択肢ツールの引数でも教訓4-4・4-22と同種の文字化け（中黒「・」が別の1文字に化けるなど）が発生した。区切り記号は、中黒より読点やスラッシュなど、より安全な記号を使う。

### 4-30. レンダリング検証は、1パターンの反復では検出できない不備がある

`v1`〜`v3` は意図的に同一入力（「指定」多め・除外あり）を使い回したが、そのため条件分岐の多く（B-05L・B-05x/B-06x・B-07-3などの不出力側）が一度も実地検証されないままになっていた（2026-09-23の `-03` で初めて検証し、問題なしと判明）。**同じパターンの反復検証に加え、条件分岐の「出ない側」を意図的に足すパターンを定期的に入れる。**

### 4-31. `edit_file` の `dryRun` は、省略すると書き込まれない

`dryRun` を明示せずに呼ぶと、差分は表示されるが実際にはファイルへ反映されない回が複数回あった（適用したつもりで、直後の読み取りで元のままと分かった）。**書き込む意図のときは、`dryRun: false` を必ず明示する。** 省略時の既定を当てにしない。あわせて、`oldText` の不一致エラーで示される「現在の内容」に文字化けが見えても、実ファイルの内容とは限らない（教訓4-28の一般化）。疑わしいときは `read_text_file` で該当箇所を取り直し、そこから得た文字列で再試行する。今回、簡体字と誤読した「阶」は、自分が `\u9636`（阶）と `\u968E`（階）を打ち間違えたことが原因と判明した例もあった（教訓4-4・4-22の「\uXXXXを使わない」を守らなかったことが根本原因）

### 4-32. 記録の「修正済み」は、実物を取り込み、`jsonschema` を入れた状態でテストを走らせて確かめる

2026-09-24、実環境のファイルを取り込んで既存テストを走らせると、`suno.json` の `bindings[4]`（E1 で削除したはずの `kind: mode`）が残っており、143件中20件が失敗した。利用者の環境には `jsonschema` がないため、表面化していなかった。**作業の最初に、実物で既存テストのベースラインを取る（`jsonschema` あり）。** 教訓4-19の再確認。

### 4-33. スキーマの `oneOf: [null, X]` は、違反したキーの場所を F1 の指摘から失わせる

`type: ["object", "null"]` の定義にして `$ref` する。`$ref` と `properties` を併用すると、親の `additionalProperties: false` は `$ref` 先のキーを見ないので、独立した定義に分ける。

### 4-34. バックグラウンド実行は `setsid nohup ... &` で行い、待つときは 285 秒以内に区切る

`nohup` だけでは、ツール呼び出しの終了で止まることがあった。変異テストは1種あたり数十秒で、4並列でも1コマンド300秒（教訓4-25）に収まらない。`sh` はプロセス置換 `<(...)` を使えない（教訓4-15）。

### 4-35. 日本語の `\uXXXX` 渡しは、2026-09-24 にも再発した
