## 5. 実装の進め方（提案。未承認。Claude Code の最初のスレッドで決める）

### 5-1. 単位と順序の案

| 単位 | 内容 | 理由 |
|---|---|---|
| U0 | Phase 0（§4）と、足場（Vite＋Vue＋TypeScript＋Nuxt UI＋VueUse＋Vitest。配置は GitHub Pages＋ローカル IIS 両対応。R-09） | 方針は決定済み（R-06） |
| U1 | データ層: `fields.json`・語彙（`specifications/presets/`）・ツールプロファイルの読み込み、楽曲データの型と検証（`song.schema.json` を共有） | 以降のすべての土台 |
| U2 | **依頼文の生成器**（純関数: 楽曲データ＋項目定義＋語彙＋ツールプロファイル → 依頼文）。`request-blocks.md`（出力条件）と `request-text.md`（文面）が正 | 中核の価値で、仕様が最も固まり、UI から独立してテストできる |
| U3 | 保存: 自動保存、ユーザープロファイル、ファイル入出力、ファクトリープロファイル、UI 設定（`song-file.md`） | データ層の上に載る |
| U4 | UI: 一覧＋ポップアップ、選択 UI（階層テーブル）、状態・値の見せ方、辞典、依頼文の表示とコピー、警告（`ui-and-nonfunctional.md`・議論ログ17） | 分類Eの確認を含む（宿題4） |
| U5 | 仕上げ: チップ化の案内（宿題42）、配置（サブパス）、検証 | — |

**生成器の正解データ（golden）の案**: 手描画のレンダリング例（`examples/`）は、検証に使った版の記録で、最新の文面とは一致しない（R-6 などの反映後は未描画）。そこで、`-12` と同じ入力を生成器に通した出力を、`-12` §1 と突き合わせ、**差が文書化された変更（R-6 の合算行）だけであること**を確かめる。ほかに、`-04`・`-06`（派生生成。第2段階）の入力 JSON が使える。正解データの入力 JSON（`-07`〜`-12`）は未作成で、U2 の中で `-08` の入力から起こす。

**アプリ側のテストの案**: Vitest（生成器・保存の規則）、jsdom の構造テスト、目視が必要な範囲は前もって明示する（教訓4-9）。

### 5-2. 設計に戻る条件

次のときは、実装を止めて設計に戻る。

- 実装の中で、仕様が曖昧・矛盾していて、実装側で決められない論点が見つかったとき（`request-text.md`・`request-blocks.md` の食い違いなど）。判断ポイントとして記録し、利用者の承認を得る（教訓4-6）
- 生成器の出力が、手描画の文面と、文書化されていない差を持つとき（文面が正。実装を直す）
- 文面の変更が必要になったとき（レンダリング例と6モデルの再検証が要る。教訓4-30）
